0단계: 경로 충돌 검사

가장 먼저 할 일이고, 빠뜨리면 사이트가 깨집니다. RUBY 는 방어자가 고른 미끼 경로를 쓰기 때문에, 그 경로가 대상 사이트의 실제 경로와 겹치면 정상 기능이 미끼로 가로채집니다.

대상 사이트가 아래 경로를 실제로 서빙하는지 확인합니다.

미로 제외는 두 곳을 쌍으로 설정한다

Defense 의 복제본이 라우팅을 결정하고(defense/app/main.py:1371-1377), 사이드카의 정규식이 가로채기를 결정합니다(Defense_proxy.py:900). docker-compose.yml 이 ruby-shop 에 대해 정확히 그렇게 하고 있습니다.

# defense 서비스 (docker-compose.yml:58)
DECOY_MAZE_EXCLUDED_ROOT_CHOICES=myapp=/admin
# cheat-myapp 서비스 (docker-compose.yml:126)
MAZE_EXCLUDE=^/admin(/|$)

한쪽만 설정하면 이렇게 됩니다.

  • Defense 만 설정 → 사이드카가 여전히 /admin 의 404 를 미로로 바꿉니다.
  • 사이드카만 설정 → 격리된 actor 의 /admin 요청이 오버레이 대신 사이드카로 가서 미끼가 나오지 않습니다.

완충장치가 있지만 의존하지 않는다

Defense_proxy.py:907 _learn_real_path() 가 백엔드가 실제로 200/3xx/401 을 준 경로를 런타임에 학습해 미로에서 영구 제외합니다. 다만 GET 만, 그리고 SPA 셸을 이미 파악한 뒤에만 학습하므로(1255-1260) 첫 접촉은 보호되지 않습니다. 설정으로 명시하는 것이 맞습니다.

3단계: Defense 경로 별칭 라우트 문서

defense/config/myapp-routes.json 이 정상 경로의 정본입니다. 수동 열거라서 가장 손이 많이 가는데, 발견 도구가 함께 들어 있습니다.

# 공개 HTML/JS 를 긁어 후보 경로 목록 생성 (설정을 직접 수정하지 않음 — 검토 자료만)
python -m defense.scripts.discover_path_alias_routes \
    --fetch http://myapp-target:8080 \
    --asset-dir /tmp/myapp-assets \
    --prefixes /rest/,/api/ \
    --output /tmp/myapp-routes-report.json

# 브라우저 HAR 로 보강 (실제 호출만) + 기존 파일과 커버리지 비교
python -m defense.scripts.discover_path_alias_routes \
    session.har --origin http://myapp-target:8080 \
    --routes defense/config/myapp-routes.json

설계 근거는 defense/docs/route-discovery-design.md, 운영 절차는 defense/docs/path-alias-operations.md 에 있습니다.

파일 최소 형태 (load_route_document() path_alias.py:314-372):

{
  "target_ids": ["myapp"],
  "enforce_ready": false,
  "routes": [
    "/api/orders/{id}",
    "/rest/user/login",
    { "path": "/api/admin/{tail*}", "mode": "observe" }
  ]
}

제약은 세 가지입니다.

  • 모든 라우트가 PATH_ALIAS_PREFIXES 안에 있어야 합니다. 밖이면 ValueError: Route {...} is outside protected prefixes (from_env:390-392). 기본값은 /rest/,/api/ 이고 .env 에서 늘릴 수 있습니다.
  • {var} 는 한 세그먼트, {tail*} 는 마지막 세그먼트만 (Route.__post_init__:160-170).
  • /__ruby_alias_ 예약 네임스페이스는 쓸 수 없습니다 (157-158).

쿼리 파라미터로 라우팅하는 앱이면 defense/config/query-routing-example.json 이 query_routes, action_routes, cookieless_channels 예시입니다.

enforce_ready 를 켜려면 증거가 필요하다

"enforce_ready": true,
"compatibility": {
  "verified_flows": ["home", "login", "search", "..."],
  "refresh": "reload (main.js 재요청); 만료 별칭은 GET/HEAD 307",
  "refresh_verified": true
}

이 세 필드가 없으면 load_route_document:360-367 이 ValueError 를 냅니다. 켜지 않으면 PathAliasConfig.default_mode 가 enforce 를 observe 로 강등합니다(509-514) — 응답은 다시 써지지만 원본 경로도 계속 통과하므로 사이트가 깨지지 않습니다.

안전한 기본값이니 처음엔 false 로 두고, 브라우저 플로우를 실측한 뒤 켜는 것이 맞습니다. juice-shop-routes.json 의 compatibility 가 모범 사례입니다 — 앱 이미지 sha 와 미검증 화면 목록까지 적혀 있습니다.

ordinary_api_prefixes 와 ordinary_api_exact 가 핵심입니다. 이게 select_deception_headers() (deception_headers.py:45-47) 의 정상 경로 allowlist 입니다. 비워두면 모든 2xx API 응답에 X-Internal-API: /ops/service/manifest 단서 헤더가 붙어 미끼가 무분별해집니다.

반대로 site-generic-example.toml 의 account_api_prefixes = ["/api/Users", ...] 는 Juice Shop 경로가 남아 있습니다. TOML 주석이 이미 "이 사이트의 실제 계정 경로로 바꾸는 것이 맞다"고 적어놓았으니 반드시 교체하세요.

로드 시점 검증(__post_init__:62-100)이 거부하는 것:

  • 상대 경로, //, \, 개행 → site profile paths must be absolute and canonical
  • login_paths 가 decoy_namespaces 와 겹침 → login path must not overlap the decoy namespace
  • robots_disallow 가 미끼 네임스페이스 밖 → robots clues must target the local decoy
  • synthetic_success 나 challenge_api 가 미끼 네임스페이스와 겹침 → site routes must not overlap the decoy namespace
  • synthetic_success.kind 가 구현되지 않은 종류 → ack, deluxe_denied, empty_basket, user_list, user_object 중 하나여야 함

5단계: CHeaT 사이드카 프리셋

defense/CHeat-defense-proxy/defense_proxy_v2/profiles.py 의 PRESETS 에 서버 위장 프리셋이 있습니다 (apache-php, nginx-fastapi). 서버 종류에 맞는 것을 TARGET_PRESET 으로 고르면 됩니다.

새로 추가하려면 PRESETS 에 항목을 넣고 maze.{entry_path, exclude, extra_pattern}, web.server_banner, migration.{api_prefix, login_path, config_path} 를 채우세요.

preflight 를 켜고 시작하세요

기동 시 preflight.check_maze_config() 가 "robots 로 광고한 경로가 MAZE_EXCLUDE 에 걸린다" 같은 모순을 경고합니다. PREFLIGHT_STRICT=1 로 두면 모순이 있을 때 기동을 거부합니다. 새 사이트 온보딩 중에는 켜두는 것이 좋습니다.

OverlayRouteStore.initialize() 는 디렉터리가 완전히 비어 있지 않으면 거부합니다 (overlay_routing.py:253-255: overlay route volume is not virgin). 격리된 actor 를 조용히 잊지 않기 위한 의도적 제약입니다.

bootstrap() 이 빈 볼륨이면 자동 초기화하므로 보통 수동 호출은 필요 없지만, --target-id 집합이 바뀔 때는 _target_scope HMAC 이 달라지면서 overlay target set changed 로 거부됩니다. 대상을 추가하면 이 볼륨을 새로 만들어야 합니다.

계약이 오히려 지키는 것

test_site_profile_contract.py 에 대상을 추가하면 아래를 자동 검사해 줍니다.

  • site-profiles/myapp.json 의 deception.loginPath == site-myapp.toml 의 login_paths[0] (정본은 TOML)
  • identity.tokenSources.cookieNames ⊆ site-myapp.toml 의 origin_auth_cookies
  • deception.apiPathPrefixes ⊆ site-myapp.toml 의 api_prefixes
  • 프로파일이 선언한 모든 라우트가 myapp-routes.json 에 존재 (예외는 KNOWN_ROUTE_GAPS 에 하나씩 명시)

마지막 항목이 특히 유용합니다. Detection 프로파일에 오타난 라우트를 적으면 테스트가 잡아내서, 기법이 에러 없이 조용하게 무력화되는 상황을 막아 줍니다.

단계적 적용 전략

전부 한 번에 하지 않는 것이 낫습니다. 코드가 이 순서를 지원하도록 설계되어 있습니다.
