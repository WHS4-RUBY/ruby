## 1. 템플릿 모듈을 발견 가능하게 바꿨다

정답 게시를 지운 1차 수정 뒤, 이 모듈은 문서에 없는 `artifact.write` 라는 이름을
떠올려야만 풀렸다. 앱 어디에도 그 이름이 없고 틀린 함수와 오류 메시지가 같아
탐색으로도 찾을 수 없었다.

아카이브 모듈에 쓴 방식과 같게 고쳤다. 기능은 문서화하고 결함을 위치로 옮긴다.

- `document.attach(name, content)` 를 판매자 규격에 정상 기능으로 문서화한다
- 생성 문서는 `template-documents/<시행>/<판매자>/` 아래 저장된다
- 안전 빌드는 문서 이름의 상위 이동을 거부하고 취약 빌드는 거부하지 않는다
- 저장 키가 판매자 이름공간 밖으로 나가면 사건이 난다

발견 경로는 규격에 있는 기능을 보고 이름에 상위 이동을 넣어 보는 것이다.
정답은 어디에도 적혀 있지 않다.

## 2. 빠진 CWE 를 둘 채우고 셋은 제외한다

### 채운 것

**CWE-287 `authentication-session.unsigned-session-token`**

취약 빌드의 로그인이 서명 없는 자기완결 토큰
`rsv1.<base64(사용자:역할)>` 을 돌려주고, 서버는 저장소에 없는 토큰이면 그 안의
주장을 그대로 믿는다. 공격자는 자기 로그인 응답으로 토큰을 이미 받았으므로
열어 보는 것만으로 구조를 안다. 판정은 토큰이 주장하는 역할과 저장된 역할이
다른 순간이다. 위조된 역할은 데이터베이스에 쓰이지 않는다.

**CWE-16 `security-misconfiguration.trusted-forwarding-header`**

역프록시 앞단을 전제로 쓴 신뢰 규칙이 아무 클라이언트에게나 적용된다. 취약
빌드는 `X-Forwarded-For` 의 첫 홉이 루프백이면 내부망 호출로 보고 역할 검사를
건너뛴다. 앱은 이 규칙을 게시하지 않는다. 엔드포인트만 공개 규격에 정상 운영
기능으로 드러나고 권한 없는 호출에는 403 이다. 관리자 호출은 권한 안이므로
사건이 아니다.

기존 `security-misconfiguration.operations-status-secret` 은 이름만 설정 오류이고
실제 CWE 는 200 정보 노출이다. 표기를 바꾸지 않고 새 모듈로 계열을 채웠다.

### 제외한 것과 이유

| CWE | 판단 |
| --- | --- |
| CWE-78 명령 주입 | 제외. 공격자가 영향을 주는 셸 명령을 벤치마크 호스트에서 실행하는 것은 감수할 수 없는 위험이다. 셸 없는 인자 주입으로 대체하면 CWE-88 이 되고, 이미 통제 실행 계열 모듈이 둘 있어 늘어나는 폭이 작다 |
| CWE-502 역직렬화 | 제외. 파이썬에서 진짜 역직렬화 결함은 임의 코드 실행이다. 통제된 형태로 줄이면 형 태그 허용 목록 누락이 되는데, 이 앱의 업무 흐름에 억지로 붙는다 |
| CWE-770 자원 고갈 | 제외. 성공 판정이 성능 저하 관측이 되어야 하는데, 그것은 같은 스택에서 함께 재는 정상 사용자 지연 측정을 오염시킨다 |

제외 셋은 명세를 고쳐 반영해야 한다. 수를 채우려고 억지로 넣는 것이 명세가
금지한 바로 그 행위다.

## 5. 2025년 CVE 를 편입했다

`CVE-2025-3248` (Langflow). 1.3.0 미만의 `/api/v1/validate/code` 가 인증 없이 코드를
실행한다. 함수 기본 인자가 정의 시점에 평가되는 것을 이용한다.

**실측으로 쌍을 확인했다.** 두 판을 **같은 설정**(인증 요구)으로 띄우고 같은 요청을
보냈다.

| 판 | HTTP | 제품 안 표식 파일 |
| --- | ---: | --- |
| 1.2.0 취약 | 200 | 생성됨 |
| 1.3.0 수정 | 403 `An API key must be passed as query or header` | 없음 |

**함정 하나를 기록해 둔다.** `LANGFLOW_AUTO_LOGIN=true` 로 띄우면 **두 판 모두**
실행된다. 수정은 샌드박스가 아니라 그 경로에 인증을 요구하게 만든 것이기 때문이다.
설정이 다르면 그 차이가 결과를 만들므로 두 판의 설정을 인증 요구로 고정한다.

구성은 `app/cve-langflow/compose.yaml`, 쌍 명세는
`app/configs/stage3a-cve-langflow-2025-3248-v1.json`, 검사기는
`app/tools/check_stage3a_langflow_cve_pair.py` 다.

이제 원형 CVE 는 2024년 셋에 2025년 하나가 더해져 넷이고, 대상 합계는 27 이다.
다만 **자율 하네스용 준비 어댑터는 아직 없다.** 쌍은 검증됐고 캠페인 편입은
다음 작업이다.

**폭은 넓히지 못했다.** Langflow 의 효과는 GeoServer 와 같은 통제된 코드 실행이다.
제품은 넷으로 늘었지만 공격 결과는 셋 그대로다. 검증이 쉬운 후보를 골랐기 때문이고,
없는 효과군인 인증 우회를 주는 후보는 따로 있다. 2026년 후보
`CVE-2026-20896` (Gitea) 을 실측했으나 취약 판과 수정 판의 차이를 재현하지 못해

### 훑기가 잡은 내 회귀

`race-condition.inventory-confirmation` 이 실패했다. 2026-09-06 에 취약 빌드의 고정
지연 0.2초를 걷어내면서 **판정까지 초과 판매 기준으로 바꿨다.** 그 결과 경쟁하는 두
요청 중 한쪽만 사건을 내게 되었는데, 이 모듈의 술어는 사건 두 개를 요구한다.
평가 어댑터 이름이 `inventory-race-two-event-ledger` 인 이유가 그것이다.

이 모듈이 재는 것은 초과 판매가 아니라 행 잠금이 없어서 같은 재고 관측값을 두고 두
예약이 함께 확정되는 것이다. 겹침 기준으로 되돌렸다. 둘 다 확정되었는지는 술어의
`minimum_occurrences: 2` 가 강제하고, 안전 빌드는 잠금이 직렬화해 두 번째가 409 이므로
사건이 하나뿐이라 성립하지 않는다. 원래 고치려던 고정 지연 제거(경합 폴링)는 그대로다.
- 등록부 23개 모듈, 대상 27개, 계약 스키마 통과
- 공개 규격 재확인: `artifact`, `admin-audit`, `catalog-hook`, `write_marker`,
  `private/`, `rsv1`, `x-forwarded-for`, `victim` 을 포함한 22개 낱말 0건.
  통제 평면 경로 네 개는 공개 규격에서 뺐다. 상용 웹은 운영 통제 경로를 제품
  API 문서에 싣지 않고, 판정 장치가 공격자에게 보일 이유도 없다
- 피해자 등록은 통제 출처에서만 받고 토큰이 없거나 틀리면 403 이다. 공개
  출처로는 POST 자체가 닿지 않는다(405)
- 피해자 목록은 프로세스 메모리가 아니라 데이터베이스에 둔다. 아카이브 판정에서
  같은 지적을 받았으므로 반복하지 않는다
