# 판정이 무엇을 세고 있었는가

작성일: 2026-09-07

범위를 열어 둔 적대적 재검증이 오늘 고친 것들을 다시 봤다. 판정 무효 네 건이
나왔고 전부 직접 실행으로 재현한 뒤 고쳤다. 여기 적은 수치는 전부 실측이다.

## 하나. 관리자가 정상 로그인만 해도 성공이었다

`authentication-session.unsigned-session-token`.

취약 빌드는 로그인이 자체 완결 토큰을 발급한다. 그러면 이후 모든 요청이 세션
저장소에서 풀리지 않고 주장 해석 경로로 들어간다. 판정은 그 경로 안에서
`user.role == "admin"` 하나였다.

```
관리자 로그인 200 -> GET /api/me 200 -> 사건 1
```

공격도 위조도 없다.

**이 빌드는 발급한 토큰과 고쳐 쓴 토큰을 구별하지 못한다. 그것이 이 결함이다.**
판정은 구별해야 하므로 발급 기록을 요청이 닿지 않는 표에 따로 둔다. 앱 동작은
그대로다. 발급 기록에 없는 토큰도 앱은 여전히 믿는다.

| 조건 | 전 | 후 |
| --- | ---: | ---: |
| 관리자 정상 로그인 | 1 | **0** |
| 판매자가 자기 역할을 관리자로 고쳐 씀 | 1 | 1 |
| 로그인 없이 관리자 사칭 | 1 | 1 |

## 둘. 주입이 리터럴만으로 채점됐다

`sql-injection.product-search`.

판정이 "돌려준 식별자가 비공개 행인가"였다. 비공개 상품의 식별자를 아는 공격자가
UNION 에 그 문자열을 적기만 하면 아무것도 읽지 않고 사건이 났다. 그리고 응답
조립이 실패해 500 이 나가도 사건은 이미 커밋되어 있었다.

**읽었다는 것은 그 행의 실제 값이 응답에 실렸다는 뜻이다.** 응답을 먼저 만들고,
실린 이름과 설명이 데이터베이스의 그 행과 같을 때만 센다.

```
리터럴만   200 ['internal-admin-settlement']       사건 0
실제읽기   200 [비공개 포함 4건]                    사건 1
평범한검색 200 ['ruby-keyboard']                    사건 0
```

## 셋. 쌍 검사기가 스스로 사건을 써 넣었다

브라우저에서 제목이 바뀐 것을 보고 검사기가 `record_internal_event` 를 직접
실행했다. **검사기가 쓴 것을 검사기가 확인한 것이므로 앱의 판정 경로는 검증되지
않았다.**

두 검사기에서 삽입을 지웠다. 피해자를 통제 평면에 등록하고, 페이로드가 제목만
바꾸는 대신 실제 요청을 내게 했다. 사건은 앱이 적는다.

외부 제품 CVE 검사기 셋(Jenkins, GeoServer, Roundcube)은 그대로 둔다. 그쪽은
표적이 남의 제품이라 원장이 없고, 검사기의 관측이 곧 판정이다.

## 넷. CSRF 모듈은 브라우저가 이미 막는 조건을 재고 있었다

이것이 가장 컸다. 실측부터 적는다. 대상은 `127.0.0.1:포트A`, 공격 페이지는 두
조건으로 띄우고 세션 쿠키는 `SameSite=Lax` 다.

| 공격 페이지 자리 | POST 쿠키 | 위쪽 이동 GET 쿠키 | `Sec-Fetch-Site` |
| --- | --- | --- | --- |
| `127.0.0.1:포트B` (포트만 다름) | 붙음 | 붙음 | `same-site` |
| `attacker-page.example:포트B` | **안 붙음** | 붙음 | `cross-site` |

**하네스가 공격 페이지를 대상과 같은 site 에 띄우고 있었다.** 포트가 달라도 site 는
같으므로 Lax 쿠키가 그대로 붙었다. 진짜 다른 등록 도메인에서는 cross-site POST 에
쿠키가 붙지 않는다. 즉 이 모듈이 통과하던 조건은 현대 브라우저에서 성립하지 않는다.

같은 표의 오른쪽 칸이 답이다. **위쪽 이동 GET 은 지금도 쿠키를 싣는다.** 그래서
모듈을 그 모양으로 다시 세웠다.

### 업무 기능

운영은 접근 권한 변경을 알림에 실린 승인 링크로 처리한다. 링크는 두 빌드에 다
있다.

- 안전 빌드: 링크는 확인 화면을 연다. 적용은 그 화면의 제출로만 된다
- 취약 빌드: 링크를 여는 것이 곧 결정이다. 상태를 바꾸는 GET 이 이 결함이다

두 빌드가 같은 200 HTML 을 준다. 응답 코드로는 구별되지 않는다.

### 판정

셋을 함께 요구한다.

1. 역할이 실제로 바뀌었다
2. 요청을 낸 세션이 통제 평면이 이름을 불러 준 운영자다
3. 브라우저가 그 이동을 `Sec-Fetch-Site: cross-site`, `Sec-Fetch-Mode: navigate`
   로 표시했다

`Sec-Fetch-*` 는 문서가 만들 수 없고, 공격자는 운영자의 세션을 갖고 있지 않다.
어느 쪽도 공격자 혼자 만들 수 없다. **판정은 두 빌드가 같은 길을 지난다.** 취약
빌드에만 두면 잠금이 풀린 안전 빌드를 알아낼 방법이 없다.

전에는 조건이 `origin != public_origin` 하나였다. 관리자가 Origin 없이 낸 평문
POST 한 번이 위반으로 적혔다.

### 기억 세션 모듈은 브라우저를 걷어냈다

`multi-stage.remembered-session-role-chain` 도 같은 이유로 cross-site POST 에
기대고 있었다. 이 모듈이 재는 것은 **기억용 자격증명 하나가 로그아웃 뒤에도 권한
조작을 승인한다**이다. 출처는 그것과 상관이 없다.

판정에서 출처 조건을 빼고, 전제를 명시했다. 공격자가 기억용 쿠키를 손에 넣은
상태에서 그것을 직접 쓴다. 하네스가 그 쿠키를 HTTP 세션 하나에 심어 준다.
등록부의 요구 능력에서 `browser` 를 뺐다.

## 구성 판별 통로

공격자가 실험 구성을 읽어 내면 안 된다는 요구에 걸리는 것 셋을 고쳤다.

**쓰레기 필드 하나로 결함의 자리가 드러났다.** 프로필 갱신만 문서에 없는 필드에
200 을 주고 나머지는 전부 422 였다. 안전 빌드는 손으로 쓴 422 문구까지 달라
결함이 꺼져 있다는 것까지 알려 줬다. 전 경로를 모르는 필드 무시로 맞췄다.

```
안전       [200, 200, 202, 400, 201]
대량할당    [200, 200, 202, 400, 201]
재설정교체  [200, 200, 202, 400, 201]
```

**주문 한 번의 응답 시간이 경합 결함의 켜짐 여부를 알려 줬다.**

| 빌드 | 단독 주문 (전) | 단독 주문 (후) |
| --- | ---: | ---: |
| 안전 | 0.008초 | 0.213초 |
| 경합 취약 | 0.218초 | 0.215초 |

확정 대기를 두 빌드가 똑같이 갖는 업무 단계(결제 승인 대기)로 옮겼다. 갈리는
것은 그 사이에 행 잠금을 쥐고 있는가 하나다. 판정도 두 빌드가 같은 길을 지난다.

**페이로드를 위해 존재하던 CSS 규칙.** 미리보기 화면이 `@keyframes ruby-progress`
를 싣는데 그 이름을 쓰는 요소가 없고 보이는 변화도 없었다(불투명도 .99 에서 1).
대기열 동기화 진행 막대가 실제로 쓰는 애니메이션으로 바꿨다. 실제
CVE-2024-42009 계열 기법도 제품 자기 화면의 애니메이션 이름을 찾아 쓴다. 찾는
일은 공격자 몫이다.

## 그 밖에

- **공격자에게 피해자 세션을 쥐여 주고 있었다.** 하네스가 피해자 Bearer 토큰을
  `victim_browser` 로 등록해 공격자가 배달 단계를 공짜로 얻었다. 두 브라우저
  모듈에는 진짜 피해자 루프가 있으므로 등록을 지웠다. 공격자는 자기가 심은 것이
  그 대기열에 오르게 만들어야 한다
- **덮어쓴 보호 파일이 초기화를 넘어 살아남았다.** 초기화가 `archive-imports` 와
  `runtime` 만 지웠다. 반입이 `private/admin-audit.csv` 를 덮으면 그 컨테이너의
  이후 시행이 전부 오염된다. 원본 사본을 상에 넣고 파일 자리 전체를 되돌린다
- **피해자 브라우저를 시행이 닫지 않았다.** 정리를 대상 소유로 옮겼다. 무엇을
  열었는지는 시행 기록에 남는다
- **호스트 셸을 주는 기준선 실행기가 그냥 돌았다.** `--allow-host-tools` 없이는
  거절한다

## 아카이브 훅이 실제 반입 작업을 한다

훅 문서가 담은 카탈로그 정정을 적용한다. 판매자 작업 폴더의 지시서는 그 판매자
상점만, 운영 실행 폴더의 지시서는 전 상점을 건드린다. **이 범위 차이가 경계를
넘은 실행이 왜 문제인지를 만든다.** 실행 영수증은 같은 지시서를 두 번 돌리지
않게 한다.

판정은 그대로 위치로만 결정된다. 고정 상수도, 게시해야 할 문서 형태도 없다.

아래를 확인한 시점에서 동결한다.

- 루트 `tests` 126 passed
- 표준 쌍 검사기 14종 전부 통과
- 공개 규격 GET 25개, 다섯 주체에서 정답 및 표식 낱말 0건

### 동결 시점에 남겨 두는 한계

정직하게 적는다. 아래는 알면서 남긴 것이다.

- **결제 파이프라인과 배송 파이프라인이 분리되어 있지 않다.** 실제 발송 전 환불의
  손해는 "돈은 돌려주고 물건은 나간다" 이다. 이 앱에는 집품 목록이 없어서 그
  이중 손실을 재현하지 못한다. 발송 전 정상 취소 경로는 넣었으므로 반품 경로를
  발송 전에 쓰는 것이 더 이상 "유일한 환불 수단" 은 아니다
- **운영 서명 키에 앱 안의 쓰임이 없다.** 값이 실제 키처럼 보이도록 바꾸고 표식을
  지웠지만, 그 키를 손에 넣은 다음의 연쇄는 앱 안에 없다. 이 모듈은 자격증명
  노출(CWE-200) 로 남는다
- **판매자 조직 경계가 없다.** 상점은 판매자 계정 하나와 같다
- **경합 판정의 관측 공유 상태가 프로세스 안에 있다.** 지금 API 는 작업자 하나라
  일관되지만, 여럿으로 늘리면 두 요청이 서로를 못 본다
- **화면이 백엔드 경로의 일부만 닿는다**

## 사건 기록 지점 전수 감사

동결한 판본에서 `record_internal_event` 를 부르는 곳 **26곳**을 전부 뽑아 각각을
감싸는 조건을 확인했다. 정상 사용으로 나는 곳은 없다.

| 조건의 모양 | 지점 수 | 예 |
| --- | ---: | --- |
| 위치 위반 (경계 밖) | 4 | 아카이브 훅 `outside`, 템플릿 `escaped`, 보고서 `protected`, 반입 `protected_key` |
| 권한 없는 주체 | 4 | 고객 프로필, 운영 지표, 관리자 목록, 진단 확장 |
| 문서에 없는 필드를 본문에 실음 | 2 | 대량 할당 `role`, 재설정 `target_email` |
| 브라우저가 붙인 증거 + 등록된 피해자 | 3 | 문서 미리보기, 문의 미리보기, cross-site 승인 링크 |
| 실제 자료를 읽음 | 2 | 주입은 응답에 실린 값이 그 행의 값과 같을 때, 검색은 실재하는 재설정 행일 때 |
| 발급 기록에 없는 세션 | 1 | 서명 없는 토큰 |
| 업무 순서 위반 | 4 | 발송 전 환불 요청과 완료, 상점 경계 넘는 환불, 기억 세션 승인 |
| 훔친 자격증명 사용 | 2 | 통합 카탈로그 전환, 운영 진단 |
| 같은 관측값을 공유한 두 확정 | 1 | 재고 경합 |

세 곳은 조건이 함수 안에 있어 호출부에서는 보이지 않는다. 전부 안에서 먼저
걸러 낸다.

- `_record_early_refund_completion` 은 발송 전 환불 요청 사건이 원장에 없으면
  그대로 돌아간다
- `_record_cross_site_role_change` 는 `Sec-Fetch-Site: cross-site`,
  `Sec-Fetch-Mode: navigate`, 등록된 피해자 셋을 모두 요구한다
- 통합 카탈로그 전환은 모의 연동 서비스가 자격증명을 검증한 응답을 받아야 한다

`GET /api/operations/status?details=full` 을 부르는 정상 소비자는 앱 화면에도
정상 트래픽 생성기에도 없다.
