# 공개 RUBY 파이프라인 소규모 확인 — 2026-10-02

이 기록은 운영 설정을 바꾸지 않은 비파괴적 확인이다. 로컬 수정 브랜치의 배포 검증이 아니며, 예비 요청을 방어 효과 실험으로 해석하지 않는다. 확인 기준 소스는 `main`의 `9003c6a`이고, 공개 서버의 실제 이미지 SHA는 읽지 못했다. 시각은 KST 기준이다.

## 실제 대상과 전달 경로

- 공개 진입점 `http://158.247.253.127/`는 `OWASP Juice Shop` 제목의 HTML을 반환했다. Defense 대시보드에도 공개 진입점의 Juice Shop 경로(`/rest/products/search`, `/api/Challenges/` 등)가 백엔드 전달로 남아 있다.
- 별도 `:8088/` 주소는 HTTP 200으로 열리지만, 이 사실은 Detection → Defense의 대상 전환 근거가 아니다. 이 확인 시점의 공개 진입점 대상은 Juice Shop이다.
- 두 대시보드에 정상 로그인하여 기록을 조회했다. 비밀번호와 세션 쿠키는 이 기록에 포함하지 않았다.

## 동일 세션의 HTTP 요청

서로 구별되는 경로의 GET 네 건을 같은 쿠키 저장소에서 순서대로 보냈다. 의심 신호는 존재하지 않는 경로의 쿼리에만 넣어 원본 데이터를 변경하지 않았다. 외부 `X-Defense-Plan`과 `X-Risk-Score`도 함께 보내 외부 정책 헤더가 적용되는지 확인했다. 이 표의 클라이언트 시간은 한 번 측정한 값이며 지연 분포가 아니다.

| 요청 | HTTP 상태 | 클라이언트 시간 | Defense 대시보드 전략/결과 | Detection 관찰 |
| --- | ---: | ---: | --- | --- |
| 정상 `/` | 200 | 43.9 ms | `none` / `forwarded` | 같은 세션에 기록 |
| 저위험 `/ruby-review-f4a69b3d-low` | 200 | 47.8 ms | `none` / `forwarded` | 같은 세션에 기록 |
| 의심 신호 `/ruby-review-f4a69b3d-high` | 200 | 49.4 ms | `none` / `forwarded` | CRS 규칙 942100, 이상 점수 5, SQLi 태그. 이후 Flow 최고 Attack 14점 |
| 후속 `/ruby-review-f4a69b3d-follow` | 200 | 262.1 ms | `delay` / `forwarded`, Defense 213 ms | 같은 Flow에 기록. Flow Automation 27점, 최고 Attack 14점 |

외부에서 제시한 `rate_limit_strict` 계획은 적용되지 않았고, 방어 대시보드의 `none`/`delay` 기록은 현재 정책의 점수 구간과 일치한다. 이 구조는 **이전 완료 요청의 점수**로 다음 요청의 정책을 고른다. 의심 신호 요청 자체는 `none`으로 통과했고, 후속 요청에 200 ms 지연이 적용됐다. 서버의 실제 백엔드 결과는 모두 HTTP 200으로 전달됐다. 현재 대시보드에는 두 계층을 잇는 공통 요청 ID가 없어 경로·시각·클라이언트 ID로 대조했으며, 이번 브랜치는 요청 ID 계약을 추가한다.

같은 IP에서 새 쿠키·다른 User-Agent의 정상 GET `/ruby-review-f4a69b3d-other` 한 건은 HTTP 200, 52.8 ms였고 Defense에는 `none`/`forwarded`, 15 ms로 기록됐다. 이 한 건은 정상 사용자 지연의 일반적 추정치가 아니다. 고위험 점수 구간을 실제로 도달하거나 차단한 운영 표본은 확보하지 못했다.

## WebSocket 및 관리 경계

- 공개 `/socket.io/?EIO=4&transport=websocket`의 업그레이드는 HTTP 101을 반환했고 Engine.IO 열림 프레임을 수신했다. 클라이언트의 namespace 프레임 뒤에는 유효한 WebSocket 응답 프레임을 확인하지 못했다. 정상적인 양방향 프레임 중계로 판정하지 않는다.
- 미인증 `/__defense/dashboard` WebSocket 업그레이드는 HTTP 403이었다.
- 미인증 GET `/__detection/api/sessions`와 `/__defense/api/snapshot`은 각각 HTTP 401이었다.
- 대시보드의 `/socket.io/` HTTP 폴링 요청은 HTTP 200과 전략 `delay`로 기록된 예가 있다. 이는 WebSocket 업그레이드·프레임과 다른 처리 경로다. 현재 Detection은 프레임 내용을 점수화하지 않는다.

## 평가 해석

09.23 피드백의 고유 접속자 메모리 부하, Stored XSS 저장·성능, IDOR 권한 식별, 방어에 따른 공격자 토큰 비용을 반영해 [평가 기록 양식](../../../templates/ruby-defense-evaluation.md)에 사전 점수와 사후 점수, 전략·백엔드 결과, 공격 성공·시간·요청·토큰, 방어자 비용과 정상 사용자 지연을 분리했다. 실제 효과 평가는 동일 조건의 무방어·프록시만·방어 반복과 독립 판정이 필요하다.

| 예비 확인 | 독립 공격 성공 판정 | 공격 시간 / 요청 | 공격자 토큰 | 방어자 AI 호출·토큰 | 정상 사용자 지연 |
| --- | --- | --- | --- | --- | --- |
| 공개 서버의 소량 GET | 없음 | 시간 미측정 / 동일 세션 4건과 별도 세션 1건 | AI 공격자를 사용하지 않아 해당 없음 | 현재 등록된 지연·제한 전략에는 AI 호출 없음 | 정상 GET 43.9 ms, 별도 정상 세션 GET 52.8 ms, 각 1회 |
| 로컬 합성 사이트의 고위험 왕복 | 없음 | 시간 미측정 / 합성 공격 요청 42건 | AI 공격자를 사용하지 않아 해당 없음 | 현재 등록된 지연·제한 전략에는 AI 호출 없음; 실행 비용 별도 미측정 | 별도 정상 GET 200만 확인, 지연 분포 미측정 |

이 표에는 공격 성공률·방어 효과 추정치가 없다. 토큰 `0`이라고 기록하지 않은
항목은 AI 공격자를 사용하지 않았기 때문이며, 방어 전략의 CPU·메모리 비용을
AI 비용으로 바꾸어 해석하지 않는다.

## 로컬 대상 왕복 검사

같은 날짜에 `scripts/check_target_switch.sh`를 로컬 임시 Docker 스택에서 실행했다. macOS 기본 Bash 3.2에서 연관 배열 구문이 실패해, 검사 스크립트의 이미지·빌드 경로 목록을 일반 배열로 바꾼 뒤 재실행했다. RUBY Market 선택 시 `RUBY_WEB_TARGET_OK`, Juice Shop 복귀 시 `JUICE_SHOP_TARGET_OK`, 최종 `TARGET_SWITCH_CHECK_OK`를 확인했다. 비공개 평가기의 내부 사건·읽기 전용 권한·초기화·네트워크 격리 검사도 모두 통과했다. 생성된 임시 컨테이너·네트워크·볼륨이 종료 뒤 남지 않은 것을 확인했다. 이는 기존 두 대상의 로컬 왕복 검사이며 제3의 실제 사이트 연결이나 운영 서버 전환을 의미하지 않는다.

변경 후 기본 `docker-compose.local.yml`도 별도 프로젝트에서 `up --build --wait`로
Detection·Defense·Juice Shop 세 서비스가 healthy가 될 때까지 기동했다. 공개
Detection 포트의 GET `/`는 Juice Shop 제목을 가진 HTTP 200을 반환했고 같은
요청 ID와 200 전달 결과가 Defense 이벤트에 남았다. 기본 CI의 실제 실행 환경과
완전히 같지는 않지만, 기존 기본 대상의 로컬 기동 회귀는 통과했다. 원래 중지돼
있던 로컬 컨테이너는 건드리지 않고 시험 자원만 정리했다.

## 로컬 제3 사이트 전체 경로 검사

이 브랜치의 Detection·Defense 이미지를 별도 로컬 Compose 프로젝트로 빌드하고,
`target-profiles/site.example.json`과 호스트의 임시 HTTP 사이트를 연결했다. 원래
중지되어 있던 `ruby-local` 컨테이너는 건드리지 않기 위해 시험 컨테이너에 다른
이름을 사용했다. 공개 Detection 포트 `127.0.0.1:8081`의 GET `/`는 임시 사이트의
고유한 화면 문구를 반환했고, 프로필의 숨은 미끼 링크가 삽입됐다. 미끼 경로는
Detection에서 404로 응답했다. Defense의 `/readyz`가 사이트 연결을 확인해
healthy가 된 뒤 Detection이 시작되는 Compose 순서를 확인했다.

동일 클라이언트의 합성 `POST /api/orders/:id` 42건에는 SQLi 문자열과 반사 XSS
문자열을 넣었다. 시험용 사이트는 요청마다 새 숫자 경로에서 입력을 HTML에
반영하고 404를 반환하도록 만들었다. 이 요청은 실제 사용자 데이터나 운영 서버에
영향을 주지 않았다. 앞선 33건은 백엔드에 전달됐고, 이어진 9건은 Defense에서
429로 끝나 백엔드 요청 수가 늘지 않았다. 42건 모두 응답·Detection 상세 기록·
Defense 이벤트의 `requestId`가 일치했다.

| 로컬 표본 | 정책 전 Attack / 확정 Attack | 전략·실제 결과 | 탐지 측 사후 기록 |
| --- | --- | --- | --- |
| 첫 합성 공격 | 0 / 0 | `none`, 백엔드 404 | 해당 클라이언트의 provisional Attack 0.283 |
| 34번째 요청 | 0.853 / 0.853 | `rate_limit_strict` + `delay`, 429·`rate_limited`, 백엔드 미도달 | Attack 0.853, 방어 신호 기록 |
| 42번째 요청 | 0.853 / 0.853 | 동일 전략, 429·백엔드 미도달 | Attack 0.853, 방어 신호 기록 |

같은 IP·User-Agent이지만 새 서명 쿠키를 받은 정상 클라이언트의 GET `/`는
`none`/200으로 원래 화면에 전달됐다. 별도의 단일 경로에 공격 문자열을 넣고
백엔드가 200을 반환한 42건의 예비 시험은 최종 Attack 0.723에 머물러
`delay`만 적용됐다. 반복 횟수만으로 429가 발생한 것은 아니다. 이 시험의
응답 시간은 소수 로컬 표본이므로 정상 사용자 지연이나 방어 효과를 추정할
근거가 아니다. 실제 제3자 사이트의 인증·쿠키·리다이렉트·TLS와 운영 부하에서는
별도 검증이 필요하다.

처음 로컬 왕복에서는 새 공격 클라이언트의 첫 요청 상세에 이전 동일 IP·UA
후보군 점수 0.726이 사후 점수처럼 보였다. 정책은 새 서명 쿠키에 따라
0/`none`이었지만 기록이 오해를 줬다. 수정 후 Detection을 재빌드해 같은
42건을 재시험한 표가 위 결과다. 첫 요청 사후 기록은 해당 클라이언트의
`provisional-client-observation` 0.283으로 표시됐고, 공유 후보군 점수는
요청별 기록에 상속되지 않았다. 새 정상 클라이언트도 요청별 Attack 0이었다.

동일 시험을 새 클라이언트 쿠키로 반복하고 마지막 거절 뒤 1.2초를 기다리자,
다음 공격성 요청은 404로 다시 백엔드에 도달했다. 즉시 이어진 요청은 429로
재차 거절됐고 두 요청 모두 두 대시보드에 같은 ID로 남았다. 이는 속도 제한의
해제와 재진입을 확인한 것이며, 탐지 점수나 공격 상태가 영구 해제됐다는 뜻은
아니다. 이 합성 표본에서 CRS는 실행 중이었고 첫 공격성 요청에 SQLi·XSS 태그,
이상 점수 25와 규칙 5개를 기록했다. 별도의 반사 XSS 전용 태그는 이 표본에서
발생하지 않았다.

## 10주차 자료와 main의 차이

10주차 자료의 Flow 4→1 병합과 Attack 33.3→83.3 재생 결과는 로컬 실험이다.
기준 `main`에는 기존 Candidate·Client Flow·Resolved Actor 구분이 있었지만,
그 실험 결과가 그대로 반영되었다고 볼 수 없었다. 이 브랜치는 근거 있는 공격
요청의 최근 60분 반복 가점과 검증된 클라이언트별 정책·요청 기록 격리를 추가했다.
위 로컬 점수는 새 합성 입력의 결과이며 10주차 수치를 재현한 값이 아니다.

10주차의 XSS SQLite안도 기준 `main`에는 없었다. 이 브랜치에서는 근거 없이
그 로컬 프로토타입을 운영 저장소로 옮기지 않았다. 현재 Stored XSS 후보는
메모리 기반이며 기본 idle TTL 1시간, 최대 2,000건·4MiB, 값당 최대 4KiB다.
제한을 2건·1,400B·1초로 낮춘 시험에서는 20건 투입 후에도 두 상한을 넘지
않았고 만료 후 0건·0B가 됐다. 프로세스 재생성 뒤 후보뿐 아니라 확정 요청
기록도 사라진다. 이 보존 한계와 장기 저장소의 성능·마이그레이션은 남은 과제다.

10주차에 실제 영향은 있었으나 탐지되지 않은 SQLi 사례는 원본 요청·응답·
페이로드가 자료에 없어 같은 조건으로 재현하지 못했다. 이번 로컬 CRS의 SQLi
태그와 429 결과는 **다른 합성 입력**의 동작 증거이며 그 미탐 사례가 해결됐다는
근거가 아니다.

## 계약 시험과 남은 운영 한계

- Detection 시험 148건 중 147건 통과, 실패 0건, 실제 CRS 바이너리를 요구하는
  1건은 호스트 바이너리 부재로 건너뛰었다. 별도로 빌드한 로컬 Detection
  컨테이너에서는 CRS가 실행 중이고 위 합성 요청에 규칙 결과가 남았다.
- Defense 시험 24건은 클라이언트별 상태·동시 변경·제한 해제/재진입,
  백엔드 응답 변형과 4MiB 버퍼 상한, 중간에 끊긴 스트림의 오류 이벤트,
  관리 경로 WebSocket 거부와 준비 검사를 포함해 통과했다.
- HTTP 요청에는 공통 ID와 전략·결과가 남지만 WebSocket의 **프레임 내용은**
  탐지·변형·프레임별 기록 대상이 아니다. 업그레이드 요청의 이전 HTTP 이력으로
  전략을 선택하고 이후 프레임은 중계한다. 공개 서버에서 관측한 Engine.IO
  namespace 교환의 완전한 왕복은 확인하지 못했다.
- 탐지 세션·XSS 후보, Defense 전략 상태·이벤트는 단일 프로세스 메모리에
  의존한다. 재시작과 다중 worker에서의 공유·보존, 장기 부하·정상 사용자 지연,
  실제 제3자 사이트의 권한 신호와 방어 효과는 별도 평가가 필요하다.
