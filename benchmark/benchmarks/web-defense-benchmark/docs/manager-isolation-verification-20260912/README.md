# 관리 UI 실제 동작과 격리 검증

확인일: 2026-09-12 KST

## 결론

별도 시험 프로젝트에서 관리 UI의 취약 모드 전환, 안전 모드 복귀와 네트워크 접근 제한을 실제 Docker 환경으로 실행했고 검사기는 19개 항목을 통과로 기록했다. 일회성 검사기의 원본과 전체 출력은 보존하지 않아 제3자가 이 기록만으로 19개 결과를 재현할 수는 없다. 이 결과는 관리 UI와 시험 스택의 기능 확인이며 공격 요청 식별, 공격 차단이나 방어 효과를 증명하지 않는다.

## 확인 결과

- 관리 API에 토큰 없이 접근하면 HTTP 401을 반환했다.
- 관리 UI가 등록 대상 34개와 지정한 시험 프로젝트 및 포트를 반환했다.
- 취약 모드 전환 뒤 32자리 시험 식별자, 현재 이미지, 모듈, Compose 원본과 API 네트워크 검사가 모두 일치했다.
- `api`, `evaluator`, `mock-integration`, `object-store`, `postgres`, `redis`, `web`, `worker` 8개 서비스가 시험 프로젝트에서 실행됐다.
- 8개 컨테이너의 Compose 원본이 모두 현재 관리 UI 작업 사본이었다.
- 공격자 네트워크의 시험 컨테이너는 `web:8080`에 접근했다. 같은 위치에서 `api:8000`, `evaluator:8000`과 `host.docker.internal:38083` 직접 접근 시도는 종료 코드 1로 끝났다. 오류 출력은 보존하지 않아 종료 원인을 더 세분하지 못한다. 공개 애플리케이션 API는 의도대로 `web:8080/api/` 프록시를 통해 접근할 수 있다.
- 공격자 네트워크에는 공개 웹 컨테이너만 남아 있었다.
- 안전 모드 복귀 뒤 모듈 값이 비었고 새 시험 식별자와 스택 자체 검사가 일치했다.
- 종료 뒤 시험 컨테이너, 네트워크, 볼륨과 이미지가 남지 않았다.
- 실행 전 존재한 기존 프로젝트 컨테이너 8개의 ID는 실행 뒤에도 같았다.

기계 판독용 요약은 [result.json](result.json)에 있다.

이 결과는 추적되는 [모듈 전환 검사기](../../app/tools/check_manager_module_switch.py)가 만든 것이 아니다. 해당 검사기는 별도의 4단계 안전판 및 취약판 pair 검사를 수행한다. 이번 19개 검사의 정확한 일회성 명령과 원시 stdout 및 stderr는 남아 있지 않으므로 `result.json`은 독립 재현 증거가 아닌 실행 기록으로 취급한다.

## 독립 검토 뒤 재검증

분리된 Codex 코드 검토에서 저장된 선택 상태를 실제 Docker 상태로 오인할 수 있는 문제, 고아 네트워크와 볼륨 재사용, 공개 API 프록시와 내부 API 직접 접근을 혼동한 문구, 재현할 수 없는 19개 검사 기록과 주소에 남는 토큰 fragment를 지적했다. 높은 심각도 문제는 없었다. 지적된 항목은 커밋 `e5e9b24e2c8e96f7875b9cb8d31a03efa9bd0046`에서 보강하거나 문구를 바로잡았다.

보강된 추적 검사기를 실제 Docker에서 한 번 실행한 명령, SQL 주입 및 경로 탐색의 안전판과 취약판 공격 성공 판정, 실시간 스택 일치와 정리 결과는 [관리 UI 상태 재검증 근거](../../evidence/20260912/manager-live-state-refresh/README.md)에 있다. Claude Code는 OAuth 인증 만료로 검토하지 못했으므로 교차 검증 완료로 표시하지 않는다.

## 발견한 기존 문제

실행 전에 이미 `ruby-web-defense-benchmark`라는 한 Compose 프로젝트 안에 두 작업 사본의 컨테이너가 섞여 있었다.

- `web`, `api`: `github-ruby-web-docs`
- 나머지 6개 서비스: `github-ruby-paper-eval`

이번 관리 UI 수정의 기본 경로는 작업 사본별 프로젝트 이름을 사용해 같은 충돌 가능성을 줄인다. 사용자가 같은 프로젝트 이름을 직접 지정하거나 수동 `docker compose`를 실행하는 경우까지 자동 분리하지는 않는다. 이미 실행 중인 혼합 프로젝트는 다른 작업에 속하므로 종료하거나 변경하지 않았다.

## 검증 도구 오류 기록

첫 예비 실행은 PowerShell 5.1이 Docker의 한글 경로를 잘못 해석해 검증 도구가 실패했다. Docker의 정상 정리 출력도 예외로 처리해 시험 이미지 태그 8개와 제거된 시험 스택을 가리키는 선택 상태가 남았다. 정확한 시험 이미지 태그만 수동으로 제거했고, Git에서 무시되는 오래된 선택 상태 파일은 시험 중 덮어써져 원본 내용을 복구하지 못했다. 제거된 스택을 가리키는 상태는 삭제한 뒤 검증 도구의 UTF-8 처리와 정리 절차를 고쳐 최종 실행을 처음부터 다시 수행했다. 추적되는 프로젝트 파일은 이 과정에서 변경되지 않았다.

## 아직 확인하지 않은 범위

- 전환 실패 때 관리 UI가 `상태 확인 필요`로 표시되는 실제 Docker 실패 경로
- 같은 작업 사본에서 관리 UI 두 개를 동시에 실행하는 경우
- 관리 UI 또는 Docker 강제 종료 직후 자동 복구
- 관리 UI에서 실제 AI 실험을 시작하고 결과를 조회하는 전체 절차
- 독립 VM에서 실행한 외부 공격자와의 격리
- XSS와 CSRF 공격 요청 식별 및 실행 차단
