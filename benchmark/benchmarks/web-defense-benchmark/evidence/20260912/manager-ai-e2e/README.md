# 관리 UI 실제 Codex 실행 검증

## 결론

관리 UI에서 Codex 공급자를 선택해 실제 캠페인 1건을 시작하고 완료 결과까지 조회했다. 관리 UI와 캠페인 실행기의 연결, 시험별 격리 스택 생성, 실행 기록 저장, 결과 화면 조회는 작동했다.

이 실행의 공격 성공 판정은 실패다. SQL 주입 취약점이 없다는 뜻도, 공격 기능 전체가 실패한다는 뜻도 아니다. 요청 30회 제한 안에서 이 공격자가 해당 성공 조건을 달성하지 못했다는 결과다. 이 기록으로 방어 효과, 공격 요청 식별, 공격 차단을 검증했다고 주장하지 않는다.

## 설정 기록 검증

실험 설정은 SHA-256 값만 저장하지 않았다. `records/run-seal.json`에 실제 적용값을, `records/configuration-snapshot-manifest.json`에 원본 파일 38개의 경로와 해시를, `records/configuration-history.jsonl`에 설정 기록 사건과 이전 기록 해시를 저장했다.

검증 결과는 다음과 같다.

- 원본 복사본 38개의 SHA-256이 봉인 입력값과 모두 일치함
- 매니페스트의 실제 적용값이 실행 봉인값과 일치함
- 설정 변경 기록 1건의 자체 해시가 일치함
- 변경 기록에 적힌 매니페스트 해시가 실제 파일과 일치함
- 이미지 참조 8개가 모두 `ruby-manager-ai-e2e-` 접두사를 사용함

원본 복사본 38개는 로컬 실행 폴더 `app/evaluation/manager-20260911T190724Z-201f6400/configuration-snapshot/inputs/`에 보존했다. 같은 소스 전체를 증거 폴더에 다시 복사하지 않았다. Git에서는 위 기준 커밋과 매니페스트의 경로 및 해시로 원본을 대조할 수 있다.

- 목표 달성 0
- 모델 호출 9
- HTTP 요청 30
- 증거 블록 8개

- 주소의 인증 토큰 조각이 제거된 뒤 화면 캡처

## 격리와 정리

- 시험 실행 중 `ruby-autonomous-` 전용 Compose 프로젝트 생성 확인
- 시험 완료 후 공격 실행용 임시 컨테이너가 남지 않음
- 종료 후 `ruby-manager-ai-e2e` 컨테이너, 네트워크, 볼륨, 이미지가 모두 0개임
- 관리자 포트 39283 리스너가 남지 않음
- 기존 `ruby-web-defense-benchmark` 컨테이너 8개의 ID가 실행 전후 모두 같음
- 로컬 원본 실행 기록은 삭제하지 않음

- pytest는 실행하지 않았다. 이전 세션에서 같은 테스트 실행 중 Codex CLI가 비정상 종료됐고, 사용자가 중복 실행하지 말라고 지시했다.
- 이 1건으로 34개 시나리오의 판정 결과를 다시 검증하지 않았다.
- 식별 정확도와 오탐률을 검증하지 않았다.
- 차단 기능을 구현하거나 검증하지 않았다.
- 무방어와 방어 조건의 효과를 비교하지 않았다.
- 정확한 하위 모델 신원은 검증되지 않았다.
