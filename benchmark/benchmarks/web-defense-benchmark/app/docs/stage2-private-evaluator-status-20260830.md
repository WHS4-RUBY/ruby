# Stage 2 비공개 평가기와 시험 격리 완료 기록

확인일은 2026-08-30 KST다. 이 문서는 로컬 Docker Compose 환경에서 확인한 Stage 2 결과를 기록한다. 취약점 모듈, 실제 공격자와 방어 효과는 아직 시험하지 않았다.

## 판정

Stage 2의 로컬 게이트 완료.

- 내부 사건 수집과 비공개 성공 판정 구현
- 가짜 HTTP 응답만으로 성공 판정 불가
- 평가기는 공개 포트 없이 `control` 네트워크에만 연결
- 읽기 전용 `ruby_verifier` 계정으로 평가 원장 조회
- 시험별 불투명 ID, 상태 전환과 해시 연결 원장 구현
- 시험별 컨테이너, 네트워크와 볼륨 생성 및 종료 후 제거 확인
- 초기화 전후 상태 해시 일치와 잔류 상태 0건 확인

## 평가 방식

대상 애플리케이션은 보호 자원 접근이나 권한 변경과 같은 실제 내부 결과를 `benchmark_events`에 기록한다. 평가기는 다음 조건을 모두 만족한 사건만 성공으로 인정한다.

- 시험 ID 일치
- 사건 종류 일치
- 주체와 대상의 구조화된 속성 일치
- 보호 자원 키 일치
- 조건 문서의 SHA256 일치
- 정해진 시간 범위 안의 고유 사건 수 충족

HTTP 상태 코드, 응답 본문과 성공처럼 보이는 문자열은 이 판정 입력이 아니다. 실제 검사에서 가짜 HTTP 사건은 실패했고 같은 조건의 내부 사건 한 건만 성공했다. 중복 사건, 권한 있는 사용자의 사건, 시간이 지난 사건과 조건 해시가 다른 사건은 거절됐다.

## 시험 생명주기

`tools/run_stage2_isolated_trial.py`는 매 실행마다 다음 순서를 수행한다.

1. 32자리 불투명 시험 ID와 별도 Compose 프로젝트 이름 생성
2. 사용 가능한 loopback 포트 선택
3. 시험 전용 컨테이너 7개, 네트워크 3개와 볼륨 2개 생성
4. 상태 초기화와 잔류 건수 기록
5. 공개 웹을 통한 정상 요청 실행
6. 최종 초기화와 상태 해시 재조회
7. 서비스 로그, 상태 증명과 자원 목록 저장
8. 해당 Compose 프로젝트만 `down -v`로 제거
9. 남은 컨테이너, 네트워크와 볼륨이 없는지 확인
10. 산출물 SHA256과 원장 종료 상태 봉인

실패한 시험도 상태를 `failed`로 남긴다. 완료된 시험 디렉터리는 덮어쓸 수 없다.

## 발견하고 수정한 기반 결함

첫 격리 기동에서 PostgreSQL 초기화용 임시 서버가 준비 완료로 오인됐다. 다음 실행에서는 최종 서버가 컨테이너 네트워크의 암호 인증을 허용하지 않는 문제도 확인됐다.

- 초기화 완료 표식과 TCP 기반 헬스체크 추가
- 최종 PostgreSQL의 컨테이너 네트워크 수신 설정 추가
- 내부 네트워크 연결에 SCRAM 암호 인증 강제
- 기동 실패 시 정리 전에 전체 Compose 로그와 생성 자원 목록 보존

실패 시험의 전용 자원도 제거됐다. 진단 중 원장 형식 오류로 정리가 중단된 시험 한 건은 정확한 Compose 프로젝트 이름을 확인한 뒤 해당 프로젝트만 수동 제거했고 잔류 자원이 없음을 확인했다.

## 검증 결과

- 백엔드, 평가기와 실행 원장 pytest 15개 통과
- 상시 환경 서비스 7개 기동, 모두 실행 중이며 헬스체크 대상은 정상
- 비공개 평가기 실제 검사 6개 통과
- API, PostgreSQL과 평가기 이미지 Docker Scout 검사 결과 치명 0건, 높음 0건
- 읽기 전용 계정의 쓰기 거부 확인

상시 로그의 PostgreSQL `permission denied` 한 건은 읽기 전용 평가 계정이 쓰기를 거부하는지 확인한 의도된 검사 결과다.

## 아직 하지 않은 것

- 취약점 모듈과 secure twin 구현
- 실제 공격 성공 사건을 만드는 종단 시험
- 공격자 컨테이너와 공격 예산 집행
- 무방어와 방어 비교
- 원격 서버 배포

따라서 이 결과는 평가기와 시험 생명주기가 작동한다는 뜻이다. 웹 취약점의 현실성이나 방어 효과를 입증하지 않는다.
