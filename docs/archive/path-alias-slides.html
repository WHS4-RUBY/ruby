01 · WHY

무엇을 알고 싶은가

알고 있던 실제 API 주소를 바로 못 쓰게 하고 현재 별칭을 찾게 만들면,
같은 30분 동안 공격 성공·소요 시간·토큰 사용량이 달라지는가?
하려는 것이 아님
  • 주소를 숨겨서 취약점을 없애기
  • 별칭을 인증 수단으로 쓰기
하려는 것
  • 공격자가 적응하는 데 드는 비용을 측정
  • 에이전트가 화면·JS에서 별칭을 찾아내도 → 그것도 유효한 결과

선행연구: WebRanz(FSE'16, URL 무작위화), Andreotti·Verticale(NetSoft'24, FaaS URI 별칭) — 적응형 LLM 공격자와 직접 비교한 실험은 확인되지 않음 → 직접 측정

03 · ROTATION (v3)

의심 행동을 하면, 그 클라이언트의 별칭만 즉시 바뀐다

이벤트 교체

direct·reject 신호 → 그 클라이언트의 별칭 전부 즉시 폐기. 알아낸 정보를 버리고 다시 찾아야 함

클라이언트별

별칭은 ruby_alias_client 쿠키에 묶임. 공격자 때문에 정상 사용자 탭이 깨지지 않음

시간 안전장치

이벤트가 없어도 30분마다 교체, 유예 1세대. 한 번 찾은 별칭이 영원히 통하지 않게

PATH_ALIAS_ROTATE_ON=direct,reject · PATH_ALIAS_EPOCH_S=1800 · enforce에서만 교체 (observe는 would_rotate 기록)4 / 9
04 · IMPLEMENTATION

구현 방식: HMAC 재계산 → 클라이언트별 별칭 테이블

v1 · HMAC (9/30)v2 → v3 · SQLite 테이블 (현재)
별칭 만드는 법secret · 시각 · 접두사로 매번 다시 계산 (상태 없음)130비트 난수를 발급해 테이블에 저장, 요청마다 조회
별칭 단위/rest/, /api/ 접두사당 1개경로·템플릿당 1개 — /rest/basket/{id}/checkout, /api/Products/{tail*}
공유·교체전원 공유, 10분마다v3: 쿠키별 발급, 의심 신호 시 즉시 교체 + 30분 안전장치
재시작·다중 worker같은 secret이면 같은 값같은 DB 파일 공유 → 재시작해도 유지 (볼륨 path-alias-data)
경로 설정접두사 목록juice-shop-routes.json — 앱 코드 수정 없이 설정 파일만

왜 바꿨나

v1: /rest/ 별칭 하나로 모든 API가 열림 → v2: 경로마다 따로 찾아야 함. v2의 10분 주기는 에이전트 행동과 무관해 효과가 안 보임 → v3: 의심 행동에 반응.

테이블을 쓴다는 것 자체가 아니라 “경로별 발급 + 클라이언트별 발급 + 의심 신호 즉시 교체”가 달라진 요인5 / 9
05 · PROXY DECISION

프록시는 요청을 네 가지로 판정한다

원칙: 깨끗한 주소만 통과. 판정을 통과한 주소만 백엔드로 가므로 백엔드가 다르게 해석할 여지가 없다.

observe / enforce. observe는 404 대신 would_block으로 기록만. 응답 치환은 8 MiB까지, 초과분은 그대로 스트리밍.

  • PATH_ALIAS_PREFIXES 직접 호출을 막을 범위

  • 쿠키 ruby_alias_client · 로그 path_alias_rotation

논의 안건: Detection은 별칭을 모른다

변환이 Defense에서 일어나므로 Detection은 /rest/user/login 대신 별칭 주소를 본다. 경로 기반 규칙(로그인 시도 추출, 비즈니스 로직 태그, 스키마 학습)이 맞지 않을 수 있다. CRS는 본문·쿼리 검사라 영향이 적다.

  • Defense가 복원한 실제 경로를 Detection에 알려 줄까?
  • 실험에서는 CRS·토큰 게이트를 observe로 두고 영향을 배제할까?
