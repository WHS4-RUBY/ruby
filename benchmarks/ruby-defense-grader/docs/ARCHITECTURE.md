# Grader 아키텍처

## 설계 목표

RUBY 프로젝트의 연구 질문은 방어가 반복·적응형 공격의 성공률을 낮추고 성공까지 시간·시도·토큰을 늘리면서 정상 서비스를 유지하는지입니다. Grader는 이 문장을 실행 가능한 판정 규칙으로 바꿉니다.

```text
고정 공격 Runner ─┐                         ┌─ 상태 Snapshot Oracle
LLM Agent Runner ─┼─> 방어 프록시 ─> 대상 ─┼─ Proof 수집기
정상 트래픽 Runner ┘                         ├─ OOB 콜백 수집기
                                             └─ Usage/Latency 수집기
                                                        │
                                      불변 artifact ─> Grader ─> report.json
```

공격 Runner, 방어 시스템, Grader는 신뢰 경계를 분리합니다. 공격자는 Grader 포트·정답 파일·호스트 파일시스템에 접근할 수 없어야 합니다. 실제 배포에서는 컨테이너 네트워크와 읽기 전용 볼륨으로 강제합니다.

## CVE-Bench에서 차용한 것

CVE-Bench는 CVE 하나를 태스크 단위로 삼고, 에이전트의 자기 보고 대신 애플리케이션 상태를 검사합니다. 파일/DB 내용 대조, 상태 체크섬, 권한 값, 외부 콜백처럼 공격 유형별 화이트박스 Grader를 두며, 기준 익스플로잇으로 Grader가 실제 성공을 탐지하는지 먼저 확인합니다. 실행 환경은 컨테이너로 재현하고 여러 번 반복해 Success@k와 비용을 측정합니다.

RUBY v0.3은 먼저 CVE-Bench의 판정 구조를 동일한 의미로 재현하고, RUBY 지표는 별도 확장 계층에 둡니다.

| CVE-Bench | RUBY Defense Grader |
|---|---|
| CVE별 공격 성공 판정 | 시나리오별 방어 전후 침해 판정 |
| 8개 공격 목표 중 하나 달성 | 동일한 8개 Oracle 중 하나 충족 |
| zero-day / one-day | fixed / adaptive agent |
| 공격 성공률·비용 | 성공률 감소 + 공격 비용 증가 + 정상성 |
| reference exploit | 방어 없는 baseline의 성공 필수 |
| `/done` 상태 검사 | 동일 `/done` 응답 + 불변 artifact 재채점 |

오프라인 artifact 방식을 택한 이유는 재채점, 감사, 논문 부록 공개가 쉽기 때문입니다. 향후 `/grade` API를 추가해도 판정 코어는 그대로 재사용합니다.

## 판정 흐름

1. 실행 manifest와 예산을 검증합니다.
2. 상태, 이벤트, 사용량 artifact가 존재하고 스키마가 맞는지 확인합니다.
3. 모든 Oracle을 실행합니다. 하나라도 유효한 침해 증거를 찾으면 해당 실행은 성공입니다.
4. 동일 시나리오에서 baseline과 defended를 공격 모드별로 집계합니다.
5. baseline 공격이 한 번도 성공하지 않았다면 방어 효과 주장을 거부합니다.
6. 보안, 공격자 노력, 정상 서비스, 증거 품질 점수를 산출합니다.

## 왜 단순 LLM Judge가 아닌가

LLM Judge는 공격 로그의 의미 분류나 실패 원인 태깅에는 쓸 수 있지만 최종 침해 판정에는 사용하지 않습니다. 공격 문자열의 프롬프트 인젝션, 모델 버전 변화, 비결정성 때문에 ground truth가 흔들릴 수 있기 때문입니다. 최종 판정은 결정적 Oracle이 하고, 사람/LLM 주석은 설명 계층으로만 추가합니다.

## 확장 지점

`src/ruby_grader/oracles.py`에 시나리오별 Oracle을 추가할 수 있습니다. 예를 들어 파일 생성, 데이터베이스 체크섬, 관리자 로그인 시각, 서비스 거부 지속시간을 구현할 수 있습니다. 각 Oracle에는 반드시 양성 PoC 테스트와 정상 동작 음성 테스트를 함께 둡니다.
