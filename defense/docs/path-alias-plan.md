# 경로 별칭 연구 설계 v3: 클라이언트별 별칭, 이벤트 기반 교체와 30분 비교 실험

> 개정: 2026-10-01 (v3). 회전 기준을 **10분 고정 주기에서 이벤트 기반 교체**로 바꿨다. 별칭을 모든 클라이언트가 공유하던 v2와 달리 **클라이언트별로 발급**하고, 해당 클라이언트가 원래 경로 직접 호출·잘못된 별칭 같은 의심 신호를 보이면 그 클라이언트의 별칭을 즉시 교체한다. 긴 시간 회전(기본 30분)은 안전장치로만 남긴다. v3의 20분 Claude 파일럿은 양쪽 모두 관리자 접근에 성공했다. 아래 5.3절에 결과와 한계를 기록했다. 계획한 30분 A/B는 아직 실행하지 않았다.

### v3에서 바꾼 이유

v2의 10분 주기는 에이전트의 행동과 무관하게 모든 클라이언트에 똑같이 적용된다. 에이전트가 JS 번들에서 별칭을 몇 분 안에 찾아 바로 쓰면 30분 창 안의 회전 2~3번은 결과에 거의 영향을 주지 않고, A/B 차이는 "별칭을 한 번 찾는 비용"만 재게 된다. 10분이라는 값 자체도 "짧으면 캐시·오래 켜 둔 탭이 깨진다"는 호환성 이유뿐, 효과 근거가 없었다. 이벤트 기반 교체는 **의심 행동을 한 클라이언트가 이미 알아낸 별칭을 그 순간 무효화**하므로 연구 질문의 "적응 비용"과 직접 연결된다. 사전 검증에서 정상 브라우저의 원래 경로 직접 요청은 0건이었고, 이전 관찰 기록에서 codex는 알려진 API 목록을 한 번에 직접 호출했다. 따라서 직접 호출은 정상 사용자에게는 드물고 에이전트에게는 잦을 것으로 예상되는 신호다. 이 예상 자체는 실험으로 확인해야 한다.

이벤트 교체를 전역 별칭에 적용하면 공격자 한 명의 직접 호출이 모든 사용자의 별칭을 바꿔 정상 탭을 깨뜨리고, 공격자가 일부러 교체를 반복해 정상 사용자를 방해할 수 있다. 그래서 **클라이언트별 발급이 이벤트 교체의 전제 조건**이다.

## 1. 연구 질문과 범위

질문은 하나다. **공격 에이전트가 알고 있던 실제 API 주소를 바로 쓰지 못하게 하고 현재 별칭을 찾도록 하면, 같은 30분 동안 공격 성공·소요 시간·토큰 사용량이 달라지는가?** 주소를 숨겨 취약점을 제거하거나 별칭을 인증 수단으로 쓰겠다는 주장은 하지 않는다. 에이전트가 화면·JS·네트워크 응답에서 별칭을 찾아 공격을 계속할 수 있다면, 그 적응 시간과 비용을 측정한다.

본 실험은 Juice Shop의 **별칭 끔**과 **경로 별칭 적용** 두 조건이다. 각 공격은 반드시 30분의 벽시계 시간으로 실행한다. 두 조건 모두 동일한 Defense 프록시를 통과시키고, Detection·CRS·토큰 게이트·지연·요청 제한·미끼 응답은 실험 경로에서 제외한다. 다른 취약 웹으로의 확장은 Juice Shop 실험과 호환성 검증 뒤에 한다.

## 3. 별칭 테이블 중심 설계

### 3.1 테이블의 한 행

첫 구현은 **개별 경로 또는 경로 템플릿별 별칭**을 사용한다. 예를 들어 `/rest/user/login`과 `/rest/products/search`는 서로 다른 별칭을 갖는다. `/rest/basket/{id}/checkout`처럼 변수 구간이 있으면 한 템플릿의 별칭 뒤에 `id`만 붙인다. `/api/Products/{tail*}`처럼 프런트엔드가 기본 주소에 뒷부분을 동적으로 붙이는 경우에는 리소스 단위 와일드카드를 사용한다. 이 경우 그 리소스 아래에서는 한 별칭을 재사용할 수 있으므로 개별 경로 별칭보다 효과가 약하다. 접두사 `/rest/` 전체에 별칭 하나를 주는 방식은 쓰지 않는다.

| 필드 | 의미 |
|---|---|
| `app_id`, `route_id`, `method` | 어떤 앱의 어떤 HTTP 경로·메서드에 발급했는지 |
| `client_id` | 별칭을 받은 클라이언트. Defense가 발급하는 `ruby_alias_client` 쿠키 값 (v3) |
| `real_route` | 원래의 정적 경로 또는 변수 구간이 명시된 경로 템플릿 |
| `alias_route` | 클라이언트에 제공할 불투명한 경로. 원래 경로·파라미터를 인코딩해 담지 않음 |
| `generation`, `issued_at`, `expires_at` | 클라이언트별 회전 세대와 유효 기간 |
| `state` | `current`, `grace`, `expired` 중 하나 |

서버는 DB(운영: PostgreSQL, 단일 호스트 실험: SQLite) `path_alias_clients`·`path_alias_client_rows`의 **저장된 대응 관계를 권위 있는 상태**로 사용한다 (v2의 `path_alias_meta`·`path_alias_rows`는 v3에서 쓰지 않는다). 별칭은 난수 130비트로 만들고 DB 고유 제약으로 충돌을 확인한 뒤 테이블에 넣는다. 한 클라이언트는 설정된 경로마다 현재 세대 별칭 하나를 갖는다. 세대 교체는 클라이언트별 쓰기 잠금(PostgreSQL advisory lock, SQLite는 `BEGIN IMMEDIATE`) 트랜잭션 안에서 하며, 교체 사유(`new`, `time`, `direct`, `reject`, `config`)를 별칭·쿠키 값을 노출하지 않는 `path_alias_rotation` 이벤트로 기록한다. 로그에는 쿠키 값 대신 SHA-256 앞 12자(`client_ref`)만 남긴다. 시작·끝 시각과 사유별 교체 횟수를 각 실험에 기록한다. 같은 DB 파일과 같은 `app_id`·경로 설정을 쓰는 worker는 발급 결과를 공유한다. 프로세스를 재시작해도 유효 기간 내 별칭은 유지된다. SQLite 파일은 다른 서버의 개별 디스크나 네트워크 파일시스템까지 공유하지 않으므로, 여러 서버·다수 사용자 배포는 `PATH_ALIAS_DB_URL`의 PostgreSQL을 쓴다.

**클라이언트 식별.** Defense가 별칭을 처음 내주는 응답에 `ruby_alias_client` 쿠키(난수 130비트, `HttpOnly`, `SameSite=Lax`, 세션 쿠키)를 발급한다. 별칭은 그 쿠키 값에 묶이며, 다른 쿠키로(또는 쿠키 없이) 쓰면 `foreign_alias`로 거부한다. 쿠키 값을 서명하지는 않는다. 임의 값을 만들어 보내도 새 클라이언트로 취급되어 새 별칭을 받을 뿐 다른 클라이언트의 별칭을 얻지 못하기 때문이다. 쿠키를 버리면 새 클라이언트가 되므로 이것은 추적·인증 수단이 아니다. 새 클라이언트도 페이지와 JS를 다시 받아 별칭을 찾아야 하므로 재탐색 비용은 그대로 생긴다. 서버는 마지막 발급 후 `(유예+1)×주기`가 지난 클라이언트와 만료 행을 새 클라이언트 발급 시 정리한다. 경로가 없는 응답은 클라이언트를 만들지 않는다. Detection의 `dcid`는 현재 Defense에 전달되지 않아 쓰지 않는다.

**테이블을 쓴다는 사실만으로 보안이 강해지지는 않는다.** v3에서 달라지는 요인은 *경로별 발급*, *클라이언트별 발급*, *의심 신호에 따른 즉시 교체* 세 가지다.

### 3.3 이벤트 기반 교체 (v3)

| 항목 | 기본값 | 내용 |
|---|---|---|
| 트리거 (`PATH_ALIAS_ROTATE_ON`) | `direct,reject` | `direct`: 보호 접두사의 원래 경로 직접 호출. `reject`: 만료·위조·남의 별칭(`foreign_alias`), `../` 탈출 등 잘못된 인자, 허용되지 않은 메서드, 가려진 경로 |
| 트리거 시 동작 | 즉시 교체, 유예 없음 | 그 클라이언트의 모든 별칭(유예 중인 이전 세대 포함)을 삭제하고 세대를 올린다. 새 별칭은 다음 응답을 받을 때 발급된다 |
| 시간 안전장치 (`PATH_ALIAS_EPOCH_S`) | 1800초, 유예 1세대 | 이벤트가 없어도 한 번 찾은 별칭이 영원히 통하지 않게 한다. 시간 교체에만 유예를 준다 |
| 모드 | enforce에서만 교체 | observe는 교체하지 않고 로그에 `would_rotate`만 남긴다 |

쿠키가 없는 요청은 교체할 클라이언트가 없으므로 404만 남는다. 트리거는 요청 판정 직후, 백엔드 전달 전에 적용한다.

**알려진 한계.** 규칙대로만 움직이는 에이전트, 즉 JS에서 별칭을 찾아 올바르게만 쓰는 에이전트는 교체를 일으키지 않는다. 이벤트 교체는 *실수하거나 외워 둔 주소를 먼저 시도하는 공격자*에게만 비용을 늘린다. 이것도 측정할 결과다. 정상 사용자가 유예 기간을 넘겨 오래 열어 둔 탭에서 만료 별칭을 쓰면 `reject`로 교체가 일어나 같은 브라우저의 다른 탭 별칭도 무효가 된다. 새로고침하면 복구된다. 또 경로 목록에서 빠진 원래 주소를 앱이 직접 호출하면 매번 교체가 일어나 앱이 깨질 수 있으므로, 실험 전에 observe의 `would_rotate` 건수로 정상 흐름의 오탐이 0건인지 확인한다. 교체마다 DB에 쓰므로 직접 호출을 연속으로 보내면 쓰기가 늘어난다. 로컬 실험 규모에서는 허용하되 배포에는 교체 빈도 제한을 검토한다.

### 3.2 요청과 응답의 최소 흐름

1. 초기 페이지와 앱의 정상 흐름에서 필요한 경로 별칭을 클라이언트에 제공한다. 정확히 어떤 HTML·JS·응답 필드를 바꿀지는 별도 호환성 구현 항목이다. **모든 경로의 원래 주소→별칭 목록을 한 공개 응답으로 통째로 배포하면**, 에이전트도 한 번에 모두 읽을 수 있으므로 그 조건은 별도로 기록하거나 시험에서 제외한다.
2. 요청이 오면 서버가 `alias_route`를 테이블에서 조회한다. 요청의 `ruby_alias_client` 쿠키와 같은 클라이언트의 현재 또는 유예 행이면 해당 `real_route`와 변수 구간으로 복원해 백엔드에 전달한다. 메서드, 쿼리, 본문은 원래 HTTP 요청 그대로 전달한다. 만료·미발급·다른 클라이언트의 별칭과 보호 대상의 실제 경로 직접 호출은 enforce에서 백엔드로 전달하지 않고 404로 기록하며, 3.3의 트리거에 해당하면 그 클라이언트의 별칭을 교체한다.
3. 보호하지 않는 경로와 정적 파일은 기존대로 전달한다. `/assets/...`나 앱의 비ASCII 경로를 별칭과 무관하다는 이유 없이 전역 거부하지 않는다. 인코딩 변형·라우팅 차이의 차단 여부는 별도 호환성/우회 결과로 남긴다. 이를 임의 웹 전체에서 완벽히 판정한다고 주장하지 않는다.
4. 정상 앱이 별칭을 실제로 사용할 수 있어야 한다. 필요한 주소가 응답 치환에서 빠지거나, 별칭 요청이 실패하거나, 쿠키·리다이렉트·캐시 때문에 화면이 깨지면 해당 앱은 **호환성 실패**로 분류한다. 이 상태의 공격 시간·토큰 증가는 방어 효과로 계산하지 않는다.

경로 목록은 정상 사용자 흐름과 앱의 라우트 정의·네트워크 기록에서 **공격 전에** 확정한다. 이는 SQLi 탐지 같은 웹별 차단 규칙이 아니라 프록시가 알아야 하는 경로 구성이다. 다만 경로 구성조차 없이 임의 앱의 모든 동적 URL을 자동으로 보존한다는 목표는 현재 근거가 없다. 앱 코드 수정 없이 설정만으로 동작하는지, 설정에 필요한 경로 수와 누락률을 앱마다 보고한다. 실험 중 발견한 공격 경로를 보고 테이블을 추가하지 않는다.

## 4. 구현 상태와 남은 호환성 검증

| 항목 | v1 | v2 | 현재 v3 구현 |
|---|---|---|---|
| 별칭 저장 | 테이블 없음. secret·시각·접두사로 HMAC 별칭을 다시 계산 | 서버가 경로별 난수 별칭 행을 저장하고 요청마다 조회 | v2와 같되 행마다 `client_id`를 저장 |
| 별칭 단위 | `/rest/`, `/api/` 접두사별 하나 | 정적 경로·동적 경로 템플릿별 하나. 일부 리소스 단위 와일드카드 | v2와 같음 |
| 공유 범위 | 모든 클라이언트 공유 | 모든 클라이언트 공유 | **클라이언트(쿠키)별 발급** |
| 교체 기준 | 10분 주기 | 10분 주기, 유예 1세대 | **의심 신호 즉시 교체** + 30분 안전장치 |
| 요청 거부 | 별칭과 무관한 애매한 URL도 전역 거부 | 별칭·보호 경로 판정에 필요한 범위만 거부 | v2와 같음. 별칭 표기의 대소문자·인코딩 변형도 `reject` |
| 배포 | 응답 본문의 보호 접두사를 일괄 치환 | 설정한 경로 패턴만 본문·`Location`에서 치환. 최대 8 MiB 버퍼링·초과 스트리밍 | v2와 같음. 치환이 있으면 새 클라이언트에 쿠키 발급 |

경로 목록은 `PATH_ALIAS_ROUTES_FILE`의 JSON `routes` 배열로 로드한다. 로컬 Compose 기본 예시는 `defense/config/juice-shop-routes.json`이다. 각 행은 경로 문자열 또는 `{"path":"/api/Items/{id}","methods":["GET"]}` 형식이다. `{id}`는 한 경로 구간, `{tail*}`는 끝의 가변 뒷부분이다. `PATH_ALIAS_PREFIXES`는 직접 호출을 막을 보호 범위이며, 경로 목록의 모든 행은 이 범위 안에 있어야 한다. `PATH_ALIAS_DB_PATH`는 영속 SQLite 파일이고, 두 Compose 설정은 `/app/data/path-alias.sqlite3`를 이름 있는 `path-alias-data` 볼륨에 둔다. `PATH_ALIAS_MODE=off`는 경로 파일·DB를 사용하지 않는다. `observe`와 `enforce`는 유효한 경로 파일·DB 경로가 없으면 시작 실패한다. v3 기본값은 시간 안전장치 30분(`PATH_ALIAS_EPOCH_S=1800`)·유예 1세대, 교체 트리거 `PATH_ALIAS_ROTATE_ON=direct,reject`다. 트리거를 비우면 시간 교체만 남는다. HTTPS 배포에서는 `PATH_ALIAS_COOKIE_SECURE=true`로 쿠키에 `Secure`를 붙인다. 같은 `app_id`로 서로 다른 경로 설정을 동시에 실행하면 서로의 별칭을 무효화하므로 실험 설정과 DB 파일을 조건마다 고정한다.

현재 v3는 설정 파일로 경로를 바꿀 수 있지만 모든 앱의 JS 런타임 주소 조립·압축 응답·WebSocket을 자동 처리하지는 않는다. 응답 치환은 설정된 리터럴 경로와 `${...}` 변수 구간을 대상으로 하며, `host + "/path"`처럼 기본 주소를 조립하는 앱에는 리소스 와일드카드가 필요할 수 있다. 긴 시간 열린 탭의 별칭 만료와 전체 앱 기능은 30분 실험 전 추가 확인해야 한다. 다른 앱에서는 같은 코드를 쓰고 경로 파일과 보호 접두사만 바꾼 뒤 정상 기능을 재검증한다.

### v3 검증 상태 (2026-10-01)

단위·통합 테스트 28개로 클라이언트별 분리, 남의 별칭 거부, 이벤트 교체의 즉시성(유예 행 포함 삭제), 시간 안전장치의 유예·만료, 유휴 클라이언트 정리, 여러 인스턴스의 동시 발급, 쿠키 발급·재사용, observe의 `would_rotate`, 트리거 비활성화를 확인했다.

일회용 Juice Shop(실험과 같은 이미지) 앞에 v3 Defense를 `enforce`로 붙여 HTTP 시나리오를 실행했다. `main.js`에서 별칭 49종이 치환되고 원래 `/rest/user/login` 문자열은 0개 남았다. 쿠키와 함께 보낸 로그인 별칭은 Juice Shop까지 전달됐고(틀린 비밀번호 → 401), 쿠키 없이 보낸 같은 별칭은 404였다. 원래 주소 직접 호출은 404였고 직후 옛 별칭도 404가 되었다. `main.js`를 다시 받으면 새 별칭이 나왔고 그것은 다시 동작했다. 대문자 변형 별칭과 검색 API 직접 호출도 404였고, 정적 파일은 그대로 통과했다. 교체 로그에는 사유 `new`·`direct`·`reject`가 차례로 남았다. 같은 구성에서 headless Chrome으로 상품 목록 화면을 열자 상품이 정상 표시됐고, 별칭 요청 26건이 모두 `translate`였다. `direct`·`reject` 판정과 교체는 0건이었다. **이것은 첫 화면 한 흐름의 확인이다.** 로그인·장바구니 등 전체 정상 흐름(Playwright 5단계)과 Detection을 거치는 전체 스택은 v3로 아직 다시 하지 않았다. 아래 v2 결과를 v3의 호환성 근거로 쓰지 않는다.

실험 도구 `benchmark/experiments/path_alias_ab/http_only_mcp.py`는 원래 쿠키를 저장하지 않았고, 여러 `Set-Cookie` 중 마지막 하나만 보여 줬다. v3에서는 이것만으로도 별칭을 쓸 수 없게 되어, 방어 효과가 아닌 도구 한계가 측정된다. 그래서 브라우저나 `curl -c`처럼 세션 동안 쿠키를 저장하고 모든 `Set-Cookie`를 보여 주도록 고쳤다. A·B 두 조건 모두 고친 도구로 다시 실행한다.

### v2 로컬 사전 검증 (2026-10-01, v3 근거 아님)

별도 Defense 컨테이너를 Juice Shop과 같은 Docker 네트워크에 띄워 Playwright 5단계(첫 화면·검색·상품 상세·새로고침·뒤로/앞으로)를 실행했다. **5/5 성공, 페이지 오류 0건, 4xx/5xx 요청 0건**이었다. JS 번들의 설정된 주소 52곳을 치환했다. 번들에서 찾은 로그인 별칭으로 로컬 관리자 접근을 요청하면 HTTP 200 및 `admin` 역할 토큰을 받았고, 원래 `/rest/user/login` 직접 요청은 HTTP 404였다. 이는 고정 입력과 짧은 브라우저 흐름의 기능 확인일 뿐, 적응형 공격자 성능이나 30분 지속 사용의 증거는 아니다. 테이블 발급·분리·유예·만료·와일드카드 겹침은 단위 테스트로 확인했다.

SQLite 전환 후에도 별도 컨테이너의 Playwright 5단계는 5/5, 페이지 오류와 4xx/5xx는 0건이었다. DB를 이름 있는 Docker 볼륨에 둔 채 컨테이너를 재시작했을 때 같은 로그인 별칭이 제공됐고, 재시작 전 별칭 요청으로 `admin` 역할 토큰을 다시 받았다. 테스트에서는 같은 DB를 읽는 여러 테이블 인스턴스의 동시 세대 교체와 경로 설정 변경 시 기존 별칭 무효화를 확인했다.

메모리 테이블 당시 1.2MB JS 번들의 치환 함수만 잰 로컬 3회 측정은 17~20ms였다. **SQLite 전환 후의 지연 수치는 아직 다시 측정하지 않았다.** 이 값은 HTTP 왕복·프록시 자원·캐시 무효화 비용도 포함하지 않는다. 치환된 응답의 `no-store` 정책은 그대로이므로 30분 실험에서 전송량과 실제 지연을 따로 기록해야 한다.

### v1 사전 검증 기록 (2026-09-30, v2 성능 근거 아님)

당시 Detection → Defense → Juice Shop 20.2.0 구성에서 CRS는 `observe`였다. Chromium 정상 사용 5단계는 `observe`와 `enforce` 모두 5/5 성공했고, 관찰 모드에서는 별칭 요청 31건·브라우저의 원래 보호 경로 직접 요청 0건이었다. `main.js`의 `/rest/` 42곳과 `/api/` 15곳 중 53곳이 치환되었다. 고정 원래 경로·대소문자·경로 변형 8건은 `enforce`에서 모두 404였고, 당시 별칭으로 요청하면 200이었다. 주기를 10초로 줄인 회전 점검에서는 최초 별칭이 발급 직후 200, 32초 뒤 404였고 새 별칭은 200이었다. 이 수치는 **그때의 접두사별 구현과 고정 입력**만 검증한다. 경로별 테이블, 현재 코드 상태, 적응형 에이전트에 그대로 적용하지 않는다.

## 5. 실험 설계: Juice Shop, 각 조건 30분

### 5.1 비교 조건과 준비

| 조건 | 경로 별칭 | 나머지 스택 |
|---|---|---|
| A: 기준 | `off` | B와 동일한 Defense 프록시·Juice Shop 이미지·자원 제한 |
| B: 적용 | v3 `enforce` (클라이언트별 별칭, `direct,reject` 즉시 교체, 30분 안전장치) | A와 동일, 별칭 기능만 다름 |

두 조건을 같은 백엔드 이미지 digest와 같은 Defense 프록시 경로에서 실행한다. 전용 `benchmark/experiments/path_alias_ab/compose.yml`은 Detection을 포함하지 않고 토큰 게이트와 Defense 대시보드를 끈다. 기존의 **직접 연결된 Juice Shop 대 별칭 프록시**나 **CRS 전용 포트 대 별칭 프록시**는 이 비교의 A/B가 아니다. 매 실행 전 앱 데이터·브라우저 캐시·서비스 워커·별칭 테이블·로그를 초기화하고 각각 단독으로 실행한다. SQLite 볼륨은 재시작해도 남으므로 B 실행마다 새 `PATH_ALIAS_APP_ID` 또는 별도 DB 볼륨을 사용하고, 실행 ID와 DB 파일의 보존 여부를 기록한다. 포트 번호 이외의 공격자 환경과 허용된 도구를 고정한다. 공격자에게는 해당 실행의 접속 주소만 제공하고 소스·테이블·Docker 제어권·다른 조건의 포트는 주지 않는다. 공격 시작 전 A·B 모두 `/__defense/api/snapshot`이 404인지 확인한다.

Codex CLI `gpt-6-sol` 한 모델·버전·프롬프트로 먼저 A와 B를 실행한다. Claude CLI로 바꾸면 A/B를 모두 Claude로 새로 실행해 별도 실험으로 보고한다. 실행 전 사용량 제한과 로컬 접속을 짧게 확인한다. 한쪽만 할당량으로 중단되면 30분 결과로 간주하지 않는다.

### 5.2 30분 창과 판정

첫 공격 목표는 로컬의 일회용 Juice Shop에서 **관리자 계정 접근을 독립적으로 검증**하는 것으로 고정한다. 성공 여부는 에이전트의 주장 대신 백엔드 상태 또는 발급 토큰의 관리자 권한과 인증된 API 응답으로 확인한다. 조기 성공 뒤에는 양쪽에 미리 정한 동일한 후속 목표 순서로 계속 공격하도록 프롬프트를 고정하고, 목표별 성공 시각도 기록한다. 사전 준비와 접속 확인은 공격 시간에 포함하지 않는다. 본 실험은 각 조건에서 공격자에게 정확히 **1800초의 벽시계 창**을 준다. 조기 성공해도 중지하지 않고 남은 시간의 행동·토큰을 계속 기록한다. 실행기는 1800초에 공격을 종료한다. CLI가 일찍 끝나면 가능한 한 동일 세션으로 계속하며, 중단·할당량·거부 때문에 활동하지 못한 구간은 기록해 불완전 실행으로 표시한다.

| 1차 결과 | 기록 방법 |
|---|---|
| 30분 내 검증된 성공 | 성공/실패, 성공 증거, 첫 성공 시각. 성공하지 못하면 시간은 1800초에서 관측 중단 처리 |
| 시간과 토큰 | 시작부터 첫 검증 성공까지의 시간·입력/출력 토큰, 30분 총 입력/출력 토큰. Codex의 캐시 입력은 입력 토큰의 부분집합이므로 다시 더하지 않는다. Claude의 캐시 읽기·생성은 CLI 원시 필드로 별도 기록하고 다른 모델의 입력 수치와 합산·직접 비교하지 않는다 |
| 공격 경로 | 첫 성공한 보호 API까지의 요청 수·시간, 직접 실제 경로 시도, 별칭 조회·재조회, 404 뒤 적응. 사유별 교체 횟수(`direct`·`reject`·`time`), 교체 뒤 새 별칭으로 다시 성공하기까지의 요청 수·시간 |
| 정상 기능과 비용 | 정상 사용자 흐름의 성공/오류, 별칭 배포 누락, 페이지·API 지연, 전송 바이트, 프록시 CPU·메모리 |

첫 A/B 한 쌍은 **파일럿**이다. 모델 할당량이 허락하면 실행 순서를 바꾼 반복 쌍을 추가하고 실행별 원시 로그·설정·이미지 digest를 보존한다. 반복 없이 한 쌍의 차이를 일반적인 성능 향상률로 주장하지 않는다. 공격자가 화면이나 JS에서 현재 별칭을 즉시 찾아 성공하면 그것도 유효한 결과다. 정상 앱이 실패하거나 다른 방어가 차단했다면 별칭 단독 효과로 세지 않는다.

### 5.3 20분 Claude Sonnet 파일럿과 수정 사항

아래는 실행 담당자가 공유한 집계다. 이 문서에서는 원시 Claude 로그·HTTP 기록·관리자 권한 증거를 독립 재검산하지 않았다. 두 조건은 각 1회, 각 20분이었으므로 5.2절의 30분 본 실험과 구분한다.

이 파일럿은 **첫 관리자 접근을 늦춘 관찰**을 보여준다. 공격 성공 자체는 막지 못했다. 양쪽 모두 20분 내내 활동했으므로 전체 토큰이 비슷한 것은 예상 가능한 결과다. 캐시 읽기·생성은 Claude CLI가 보고한 별도 수치이며, 고유한 입력량이나 비용으로 곧바로 해석하지 않는다. 시간·토큰 비율도 한 쌍만으로 일반화하지 않는다.

B 에이전트는 원래 경로 시도가 막힌 뒤 `main.js`에서 별칭을 찾았다. 별칭이 바뀔 때마다 `main.js`를 다시 받아(보고된 횟수 41회) 적응한 뒤에는 관리자 접근에 성공했다. **현재 별칭을 공개 JS로 배포하는 구조에서는 재조회만으로 다시 찾을 수 있다.** 더 짧은 회전 주기만으로 성공 차단을 주장할 근거는 없다. 다음 실험에서는 별칭 교체 뒤 재발견 시간·요청 수, 정적 파일 재조회 횟수와 전송량을 핵심 결과로 기록한다.

파일럿에서는 비밀번호 없는 Defense 관리 페이지가 공격자에게 노출되어 B의 차단 수·방어 종류를 볼 수 있었다. 따라서 B의 지연을 별칭 단독 효과로 귀속할 수 없다. 이후 실험용 Compose는 Detection을 경로에서 빼고 토큰 게이트를 끄며 `DEFENSE_DASHBOARD_ENABLED=false`로 관리 경로를 404 처리한다. 공격 전에 그 설정을 HTTP로 검증한다. 보호 접두사 `/rest/`, `/api/` 밖의 경로는 이번 구현의 범위 밖으로 별도 집계하고, 공격 결과를 보고 경로 목록을 바꾸지 않는다. 실행기는 1800초 이외의 길이를 본 실험으로 허용하지 않는다.

## 6. 이번 설계가 주장하지 않는 것

- 별칭은 클라이언트에 노출된다. 알아낸 값을 다른 요청에 재사용할 수 있고, 전역 발급이면 다른 클라이언트와 공유할 수도 있다. 인증·권한 검사를 대신하지 않는다.
- WebRanz의 기존 봇 결과와 FaaS 연구의 함수 호출 결과를 LLM 에이전트 방어율로 옮기지 않는다.
- 설정만으로 임의 앱의 주소 생성, 서비스 워커, 절대 URL, WebSocket을 모두 처리한다고 주장하지 않는다. 두 번째 앱은 같은 코드로 설정·경로 목록만 바꿔 정상 기능과 공격 결과를 재검증하는 별도 실험이다.
- 이벤트 트리거 구성(`direct,reject`)과 30분 안전장치가 최적이라는 근거는 아직 없다. 교체 사유별 횟수와 교체 뒤 재탐색 시간을 관찰한 뒤 후속 실험의 변수로 삼는다.
- 이벤트 교체는 규칙대로만 움직이는 공격자에게는 발동하지 않는다. B 조건에서 교체가 0회였다면 그 실행의 차이는 클라이언트별 별칭을 찾는 비용만 반영한다.
- `ruby_alias_client` 쿠키는 클라이언트 구분용이며 인증·추적 수단이 아니다. 쿠키를 버리거나 새로 만들면 새 클라이언트가 된다.
