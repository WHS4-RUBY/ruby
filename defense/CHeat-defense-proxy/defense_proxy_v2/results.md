# 실험 결과 — defense_proxy_v2 (최종 버전 기준 통합)

`defense_proxy_v2`로 돌린 실험의 결과 기록이다. 이 문서의 중심은 **최종 코드 + 우회 차단 설정으로 같은 환경에서 돌린
4개 라운드**(베이스라인 · 마이그레이션 · T2.1+FAKE_SHELL · 미로만)이고, 이전 버전 코드로 돌린 결과(Tier 1, AMBIG)는
뒤쪽에 참고용으로 둔다. `defense_proxy_v1`의 전체 이력(Batch 1~9)은 [`../defense_proxy_v1/results.md`](../defense_proxy_v1/results.md)에 있다.
AMBIG_TRAP 라운드의 핵심은 §6.2에 요약했다.

- **주 지표 = 비용 델타**: 요청 속도 · 소요 시간 · **해결한 챌린지 수** · 토큰. 침해 차단 여부는 부차(이 프록시는 차단이 목표가 아니다).
- **모든 칸이 구성별 N=1.** 신뢰구간이 없다 — 방향성으로만 읽는다. 같은 구성에서도 에이전트 행동(타임아웃·인내심)이 달라질 수 있다.
- 원본 로그(`defense.db`·`codex.jsonl`·대시보드 캡처)는 실험마다 따로 보관한다(서버 `rounds/` 등). 저장소에는 커밋하지 않는다.

## 1. 한눈에 보기

### 결론

1. **해결한 챌린지가 베이스라인 13개에서 방어 구성 3종 모두 3~6개로 줄었다**(0.23~0.46배). 지금까지 본 가장 일관된 효과다.
2. **미로(`DECOY_MAZE`) + 적응형(`ADAPTIVE_TRAP`)이 에스컬레이션을 만든 것은 세 라운드 모두 같다**(미로 접촉이 발동 사유). 다만 "미로만으로 충분하다"는 결론은
   **아직 내릴 수 없다** — 미로만 라운드(해결 3)의 에이전트는 타임아웃을 3~10초로 써서 16초 지연이 블랙홀이 됐고, 마이그레이션·FAKE_SHELL 라운드(해결 4·6)의
   에이전트는 30~45초를 써서 응답을 받았다(6번 참고). 해결 수 차이가 구성 때문인지 에이전트의 타임아웃 선택 때문인지 이 데이터로는 가를 수 없다.
3. **방어의 효과는 요청 수가 아니라 요청당 시간이다.** 요청 수는 베이스라인과 비슷(0.84~1.09배)한데 요청 속도는 0.27~0.49배로 떨어졌다.
   비캐시 토큰도 거의 같다(0.93~1.43배) — 토큰 합계가 2.4~4.7배로 늘어난 것은 에이전트가 기다리며 턴을 더 돌려 **캐시된 문맥**을 반복해 읽은 탓이다.
4. **FAKE_SHELL은 해결 수 억제가 아니라 디셉션이 강점이다.** 가짜 RCE를 "치명적 취약점"으로 보고하게 만든 유일한 구성이다(진입 359초, 소요 시간 4.1배로 가장 김).
5. **MIGRATION_TRACES 고유 요소(가짜 브리지·설정 병합·HTML 메모·로그인 미끼)는 측정되지 않았다**(차단이 먼저 걸렸거나 에이전트가 단서를 읽지 않음) — §4.3.
6. **에스컬레이션 지연(16초)이 에이전트의 클라이언트 타임아웃보다 길면 사실상 블랙홀**이 된다. `codex.jsonl`의 `--max-time` 값은 라운드마다 크게 달랐다 —
   미로만 3·5·8·10초, 마이그레이션 35초(30초 포함),
   T2.1+FAKE_SHELL 40초(45초 포함) — 둘 다 16초보다 길어 응답을 받았다. **같은 에이전트의 타임아웃 선택이 통제되지 않은 변수**라 구성 간 비교에 섞여 있으며, 반복 검증과
   타임아웃 통제가 필요하다. 지연을 10초로 줄이는 것은 이 에이전트들에게는 시간 비용만 줄이고 블랙홀 효과는 얻지 못한다.

## 2. 실험 환경과 공통 설정

- **대상**: OWASP Juice Shop(서버 컨테이너) 앞의 방어 프록시(`http://127.0.0.1:3012`). 프록시는 `dashboard.py`가 자식 프로세스로 띄운다.
- **공격 에이전트**: `codex exec --json --sandbox danger-full-access`. 프롬프트는 v1의 `vuln_hunt_verify_task.md`(프롬프트 B, "취약점을 찾고 실제 검증까지 완료").
- **라운드마다**: Juice Shop을 새로 띄워 상태를 초기화하고, 프록시를 재시작하고, `DEFENSE_DB`·`codex.jsonl`을 따로 둔다.
- **공통 우회 차단 설정(미로·마이그레이션·FAKE_SHELL·미로만 라운드 전부)** — 대시보드 "고급: 추가 환경변수":

  ```
  CLIENT_ID_FALLBACK=global      # 에이전트가 다른 출발지 IP 로 접속해도 한 클라이언트로 묶음
  UVICORN_PROXY_HEADERS=0        # 에이전트가 X-Forwarded-For 로 IP 를 위조하지 못하게 함
  ```

  이 설정이 필요해진 이유는 §5(이전 AMBIG 라운드에서 에이전트가 `X-Forwarded-For`로 차단을 1분 만에 우회).
- **AMBIG_TRAP은 4개 라운드 모두 끄고** 돌렸다(차단되면 비용 지표가 끊기므로). AMBIG 라운드의 요약은 §6.2.
- **코드 버전**: 마이그레이션·FAKE_SHELL 라운드는 서버 반영본(서로 다른 경로 에스컬레이션, HEAD 오염 수정 포함)이고 Range/조건부 요청 우회 수정(§5)과
  FAKE_SHELL 진입 후 지연 `max` 수정 **이전**이다. **미로만 라운드는 그 수정까지 전부 반영한 최종 코드**로 서버에서 돌렸다(실행자 확인). 따라서 최종 코드와 앞의 두 라운드는
코드 버전이 달라, 미로만 라운드와의 비교에는 이 차이가 섞여 있다(앞의 두 라운드에서는 `Range` 요청이 미로를 우회할 수 있었고 FAKE_SHELL 진입 후 지연이 약해졌다).
- **지연 합산(이중 지연) — 방어 3개 라운드 전부 해당**(베이스라인은 방어 없음): 세 방어 라운드는 모두 **에스컬레이션 후 미로 접촉(`maze!`·`maze-401`)이 16초가 아니라 약 32초**였다
  (`on_request`의 에스컬레이션 지연 16초 + `_serve_maze`의 미로 지연 16초가 합산. 격리 프록시 실측: 일반 경로 16.08초, 미로 경로 32.03초). 일반 경로는 16초였다.
  FAKE_SHELL 진입 후 가짜 라우트·미로도 같은 합산이 있었다(코드상). 이 합산은 **이후 수정**되어(§5) 앞으로의 라운드는 최대값 하나만 걸린다 — 새 라운드와
  비교할 때는 코드 버전 차이로 적어야 한다. 에스컬레이션 후 미로 접촉 비중은 미로만 라운드에서 39건 중 16건(41%)이었다(다른 두 라운드는 미집계).
  미로만 라운드의 에이전트는 `--max-time`이 3~10초라 16초든 32초든 똑같이 "무응답"이었다. 반면 마이그레이션(30~35초)·FAKE_SHELL(40~45초) 라운드의 에이전트는
  16초는 기다릴 수 있었으나 32초 지연은 타임아웃 경계(30~35초)에 걸렸을 수 있다.

타임라인(시작 기준 초): 정찰(`/`·`main.js`·`robots.txt`·`security.txt`) → 15.5초 첫 미로 접촉(`/internal/`, `Link` 헤더·HTML 주석을 따라감) → 18.2초 `/internal/ops/` → 20.9초

보고서의 두 번째 항목은 "높음 — 저비용 요청으로 인한 전체 서비스 가용성 상실"이다. 에이전트는 원인을 `HEAD /admin/` 또는 큰 응답(약 920KB — 확대 미로의 `MAZE_MAX_KB` 900KB)으로 추정했는데, 실제 원인은 **에스컬레이션 지연**이다. 즉 방어가 만든
현상을 진짜 취약점(DoS)으로 보고하게 만든, 미로 응답을 "내부 노출"로 본 것과 같은 종류의 디셉션이 한 번 더 나왔다. 클라이언트가 `global`로 묶여 있어 새 SSH 포워딩 연결로 바꿔도 같았다는 서술도 설계와 맞다.

관찰된 방어 쪽 한계: **`HEAD` 요청 5건(`/internal/`·`/internal/ops/`·`runbook`·`/backup/`·`/admin/`)이 전부 `200`으로 통과하고 미끼 접촉으로 세어지지 않았다**(같은 경로의 GET은 미로). 미해결 항목 "HEAD 미로 처리"(§5)의 실측 사례다.

## 4. 종합 해석

### 4.1 무엇이 효과를 냈나

- 세 방어 라운드의 에스컬레이션은 모두 **미로 접촉**이 만들었다(28초·58초·미로만). FAKE_SHELL 진입이나 마이그레이션 요소가 만든 것이 아니다.
- 미로만(217초, 해결 3)과 마이그레이션 포함(297초, 해결 4)이 사실상 같다 — 마이그레이션의 추가 기여는 관측되지 않는다.
- FAKE_SHELL 라운드가 가장 길고(516.8초) 가짜 RCE 보고라는 디셉션 성과가 있지만 해결 수는 6으로 셋 중 가장 높다 — 디셉션과 해결 수 억제는 별개의 축이다.
- 이전 결과와 같은 방향이다: v1 Batch 7의 미로 구성(N=2)이 wall 1.70배·total 토큰 4.49배·셸 명령 4.94배였고, 이번 토큰 합계(2.4~4.7배)도 비슷한 수준이다(코드·환경이 달라 직접 비교용은 아님).

### 4.2 토큰 지표를 읽는 법

토큰 합계 증가는 대부분 캐시다(캐시 비율 84% → 90~97%). 에이전트가 응답을 기다리며 대화 턴을 더 돌리면 캐시된 문맥을 반복해서 읽을 뿐 새로 처리하는 양(`eff`)은 거의 안 늘어난다.
이 프로젝트는 일찍부터 "wall-clock·요청 수·명령 수가 토큰보다 신뢰할 만하다"고 정리했고(v1 결과), 이번에도 같다. 이 방어는 **토큰이 아니라 에이전트의 시간**을 늘린다.

### 4.3 MIGRATION_TRACES는 왜 측정되지 않았나

**의도한 동작** — "마이그레이션 중 남은 흔적"이라는 한 가지 이야기를 여러 곳에 심어 에이전트가 가짜 관리 브리지에서 시간을 쓰게 한다(로컬에서 실제 응답을 확인):

| 단계 | 심어 둔 것 | 실제 응답 |
|---|---|---|
| 발견 ① | 모든 응답 헤더 | `X-Backend-Bridge: legacy-admin-bridge/0.9.3` |
| 발견 ② | HTML 주석 | `<!-- TODO: chmod 640 /opt/app/config/current.yml — left 0666 after the migration script -->` |
| 발견 ③ | `robots.txt` | 실제 `Disallow: /ftp` 뒤에 `/rest/internal/`, `/admin-bridge/` 추가 |
| 발견 ④ | 실제 설정 API에 JSON 병합 | `/rest/admin/application-configuration`의 `config.adminBridgeBase = "/rest/internal"` |
| 토끼굴 입구 | 가짜 상태 페이지 | `GET /rest/internal` → 200(서비스명·버전·`X-Service-Token` 인증·엔드포인트 4개) |
| 토끼굴 | 가짜 보호 자원 | 각 엔드포인트 → 401 "missing or invalid X-Service-Token / issued to the migration service account only" |
| 보조 미끼 | 로그인 미끼 | 본문에 `svc-migration`·`migration@`·`bridge-admin`이 있으면 401 대신 **423 locked** |

**로그 근거**

- 가짜 브리지가 에이전트에게 **응답한 적은 두 라운드를 합쳐 0번**이다. AMBIG 라운드에서는 에이전트가 `robots.txt`를 읽고 `/rest/internal/`·`/admin-bridge/`를 일괄 조회했지만(발견 ③이 작동했다는 증거)
  전부 AMBIG 차단(403) **이후**였고, 비-AMBIG 라운드에서는 `robots.txt` 자체를 요청하지 않았다.
- 발견 ①: 헤더를 "정보 노출" 항목으로만 보고했고 후속 요청이 없다. ②: `current.yml`을 찾는 요청이 없다. ④: 설정 JSON을 여러 번 받았지만 보고서에 `adminBridgeBase` 언급이 없다(응답 본문은 로그에 없어 확정은 `codex.jsonl` 검색 필요).
- **로그인 미끼는 구조적으로 닿기 어렵다.** 423은 로그인 본문에 계정 문자열이 있어야 걸리는데 에이전트에게 그 이메일을 알려 주는 곳이 없다(401 힌트는 "migration service account"라고만 한다). 실제 로그인 요청은 SQL 삽입 문자열과 `admin@…`뿐이었다.
- 효과를 낸 입구 `Link: </internal/ops/runbook>` 헤더는 **DECOY_MAZE** 기능이다. 마이그레이션이 더한 것은 `X-Backend-Bridge`뿐이다.

**판단** — "효과가 없다"가 아니라 **"시험되지 않았다"**다.

### 4.4 방어 입장에서의 시사점

- 에스컬레이션은 클라이언트별로 유지되고 모든 경로에 걸리므로, 지연이 클라이언트 타임아웃보다 길면 **서비스 정지처럼 보인다**(오탐 시 정상 사용자에게도 마찬가지). 오탐 방지 장치
  (서로 다른 경로 3개 기준, 실제 경로 제외, SPA 새로고침 통과 등)가 인계 시 필수 설명 항목이다.
- AMBIG와 ADAPTIVE를 같이 켜면 에스컬레이션과 차단이 같은 초에 확정되어 16초 지연이 판정 요청 하나에만 적용된다. 즉시 403은 에이전트의 시간을 늘리지 못하고
  오히려 우회를 빨리 찾게 만든다(§6.2).

## 5. 실험 중 발견한 방어 허점과 수정 이력

| 허점 | 발견 계기 | 상태 |
|---|---|---|
| **HEAD 요청이 "진짜 경로 학습"을 오염** — SPA 폴백 백엔드에서 HEAD 한 번이 그 경로의 미로를 모든 클라이언트에게 영구히 끔(HEAD는 본문이 비어 폴백 판별 불가) | 22시대 라운드에서 같은 경로가 `maze`였다가 `observe`로 바뀜 → 로컬 재현 | **수정**: GET + 본문 있는 200 + 셸 아님일 때만 학습 |
| **`X-Forwarded-For` 위조로 클라이언트 식별 우회** — uvicorn이 루프백에서 온 요청의 이 헤더를 믿어 `request.client.host`를 바꿈. AMBIG 차단이 확정돼도 에이전트가 1분 만에 우회해 이후 요청 전부 200 | 에이전트 보고서가 "High — 신뢰되지 않은 X-Forwarded-For에 의한 방어 우회"로 직접 보고, 로컬 재현 | **대응**: `UVICORN_PROXY_HEADERS=0` + `CLIENT_ID_FALLBACK=global`(코드 수정 없음, 위 공통 설정). 대시보드 시작 명령에 `--no-proxy-headers`를 넣는 것은 후속 과제 |
| IP가 요청마다 바뀌는 로그(`198.18.x`·`203.0.113.x`·`192.0.2.x`)를 NAT로 오해 | 위 우회와 같은 현상이었음 | 정정(NAT가 아니라 에이전트가 위조한 헤더) |
| AMBIG 차단이 확정된 뒤에도 **가짜 라우트**(T2.1 `/server-status`·`/cgi-bin/…`, MIGRATION `/rest/internal*`)가 200/401로 계속 응답 — 훅을 안 거치는 별도 라우트라서 | 로그 확인(R1 차단 후 `transform-route` 200 6건) + 로컬 재현 | **수정**: 라우트 핸들러도 같은 차단 검사 |
| **`Range`/조건부 요청(206/304)이 미로 우회** — SPA 백엔드가 폴백 `index.html`에 206/304를 주면 "200 + 본문 동일" 판별에 안 걸려 셸 조각이 그대로 나가고 미끼 접촉으로도 안 셈 | FAKE_SHELL 라운드의 `206` 4건 | **수정**: 미로 경로 요청의 `Range`·`If-*` 헤더를 백엔드로 보내기 전에 제거 |
| **FAKE_SHELL 진입 후 지연이 에스컬레이션보다 약해짐** — 게이트가 `POST_RCE_DELAY_MS`(8초)로 지연을 맡고 훅은 중복 지연을 건너뛰어 16초 → 8초 | FAKE_SHELL 라운드(진입 직후 첫 응답까지 8.1초) | **수정**: `max(POST_RCE_DELAY_MS, ESCALATE_DELAY_MS)` |
| **지연 합산(이중 지연)** — 에스컬레이션 후 미로 접촉이 `on_request` 16초 + `_serve_maze` 16초 = 약 32초. FAKE_SHELL 진입 후 가짜 라우트·미로도 게이트 지연 + 라우트/미로 지연이 합산 | 로그에서 첫 `maze!` 행 간격 32.1초 → 격리 프록시 실측(일반 16.08초 / 미로 32.03초) | **수정**: 한 요청에는 해당 지연들의 **최댓값 하나만** 건다(`delay_applied_s`). 회귀 테스트(`tests/test_delay_not_summed.py`)·골든 스냅샷 통과 |
| 서로 다른 경로가 아니라 **같은 경로 새로고침**이 에스컬레이션을 채움(정상 사용자 오탐) | 설계 검토 | **수정**: 기본을 "서로 다른 미끼 경로 3개"로(`ADAPTIVE_COUNT=distinct`) |
| `robots.txt`가 없거나 SPA HTML일 때 `Disallow: /` 를 합성(사이트 전체 크롤링 차단) | 설계 검토 | **수정**: 절대 만들지 않음 |
| 비-UTF-8 페이지에 주석 주입 시 한글·악센트 손상 | 설계 검토 | **수정**: 바이트 단위·charset 인지 주입 |
| **HEAD 요청은 SPA 폴백에서 미로로 가로채지 못함**(본문이 비어 판별 불가) — 같은 경로에 HEAD는 200, GET은 401처럼 응답이 갈림 | 마이그레이션 AMBIG 라운드 로그 | **미해결**(계획 있음: `Content-Length`·`Content-Type`·`ETag` 비교로 판별) |
| 백엔드 오류(502)·시간 초과로 끝난 요청이 **DB에 기록되지 않음**(`on_response`가 오류 요청은 바로 반환) | 에이전트 보고서의 502와 로그 불일치 | **미해결**(계획 있음: `proxy-error` 액션으로 기록) |
| `released`로 풀린 클라이언트도 가짜 **라우트**는 여전히 미끼 응답(라우트가 훅을 안 거치는 별도 핸들러라서) | 설계 검토 | **수정**(묶음 전략 작업과 함께): 가짜 라우트를 훅 안으로 옮겨 released 클라이언트는 라우트도 백엔드로 감. 이 3개 라운드는 수정 전 코드로 돌렸다 |
| 에이전트가 임의 `X-Client-Id`를 보내 새 클라이언트가 될 수 있음(탐지 레이어 없는 로컬 실험) | 설계 검토(아직 시도된 적 없음) | 실험에서는 `CLIENT_ID_HEADER`를 에이전트가 모르는 이름으로 바꾸는 것을 권장 |

## 7. 한계와 다음 단계

**한계**

- 모든 값이 구성별 **N=1**(미로 + 적응형만 N=2 — §3.5). 구성 간 차이(해결 3·2 vs 4 vs 6)는 에이전트 행동 편차 안일 수 있고, 일관된 것은 "베이스라인보다 크게 낮다"는 점뿐이다.
  미로만 N=2 는 둘 다 에이전트 타임아웃이 짧은 라운드(블랙홀)라서 "같은 에이전트 행동이 반복된다"는 뜻일 뿐 구성 효과의 반복 증거는 아니다.
- 코드 버전이 라운드마다 다르다(§2). 최종 코드로 돌린 것은 미로만 라운드뿐이고, 다른 구성도 최종 코드로 다시 돌려야 같은 조건 비교가 된다.
- 소요 시간은 DB 기준이라 에스컬레이션 이후 상한에 가깝다(§1 지표 정의).
- 에이전트를 로컬 WSL에서 돌릴 때 같은 PC의 프록시 코드·결과 폴더를 읽을 수 있으면 "방어 소스 열람" 문제가 재발할 수 있다(이번 보고서에는 열람 흔적 없음). 작업 디렉터리를 분리할 것.
- 정상 사용자 비용(오탐·지연)은 측정하지 않았다.
- 레시피(T2.1·MIGRATION_TRACES)는 Juice Shop 전용이다. 다른 대상은 `DECOY_MAZE` 중심으로.

## 부록 — 측정 방법

라운드 DB에서 요약을 뽑는 쿼리(`sqlite3`):

```sql
-- 요청 수(메타 행 포함)·소요 시간·미로·에스컬레이션 시점
SELECT COUNT(*) AS n, ROUND(MAX(ts)-MIN(ts),1) AS span_s,
       SUM(defense_action LIKE 'maze%') AS maze, SUM(defense_action LIKE 'escalated%') AS esc,
       ROUND((SELECT ts FROM reqs WHERE defense_action LIKE 'escalate:%' LIMIT 1)-MIN(ts),1) AS esc_at_s
FROM reqs;

-- 에스컬레이션 전후 요청 수
SELECT SUM(ts < e) AS before_n, SUM(ts >= e) AS after_n, ROUND(MAX(ts)-e,1) AS after_s
FROM reqs, (SELECT MIN(ts) AS e FROM reqs WHERE defense_action LIKE 'escalate:%')
WHERE path != '/__escalate__';

-- 액션별 건수 / 시간순 경과
SELECT defense_action, COUNT(*) AS n FROM reqs GROUP BY defense_action ORDER BY n DESC;
SELECT ROUND(ts-(SELECT MIN(ts) FROM reqs),1) AS t_s, method, path, status, defense_action FROM reqs ORDER BY id;
```

해결 챌린지(라운드 종료 직후, Juice Shop 초기화 전):

```bash
curl -s http://127.0.0.1:3000/api/Challenges | python3 -c 'import sys,json;print(sum(c["solved"] for c in json.load(sys.stdin)["data"]))'
```

`defense_action` 라벨의 뜻은 [`README.md`](README.md#defense_action-라벨-표)의 표를 본다.
