# 축 분석의 읽기 기억과 묶음별 비용 몫 수정

읽은 창을 묶음이 끝날 때까지 보존하고, 축 분석 풀을 남은 묶음 수로 나누도록 수정했다. 몫을 소진하면 추가 읽기 없이 답하는 호출을 한 번만 수행한다. 최종 소스의 `py_compile`과 4달러, 1회 설정의 `--dry-run`은 통과했다. 원본과 모델을 사용한 검증은 실행하지 않았다.

## 원인 확인

체크아웃의 `.tmp/site-analysis/wordpress-analysis.verify.json`을 읽기 전용으로 확인했다. `navigation` 호출은 35회, `group_appearance` 호출은 33회였으며 다른 축 묶음 호출은 없었다. 총 비용은 4.0267612달러, 둘러보기 비용은 2.0321788달러, 상한은 4달러였다. `unobserved_axes`는 `[51]`, 종료 사유는 `cost_budget`이었다. 이동 기록은 9개였다. 서로 다른 페이지 9개라는 관찰은 사용자가 제공한 실제 검증 사실로 반영했다.

수정 전 `answer_group()`은 읽은 창을 `observer.feedback`에 추가했다. `model_context()`는 최근 피드백 하나만 별도 표본으로 앞에 넣었다. 과거 피드백은 큰 전체 목록 참조 뒤에 남았지만, 그 전에 최신 화면 표본이 창을 채우면 읽었던 여러 창의 값과 읽기 범위 목록이 다음 입력에서 빠졌다. 원문 자체가 삭제된 것은 아니지만 모델에게 전달하던 읽기 기억이 유지되지 않는 경로였다. 여러 페이지의 근거를 함께 보아야 하는 축에서 같은 읽기를 반복할 수 있는 구조이며, 모델의 실제 내부 판단까지 이 기록으로 복원할 수는 없다.

`semantic_merge()`도 새 읽기마다 `feedback`을 하나의 창으로 교체했다. 유효한 축을 제거하면 `provided-context`의 내용과 offset의 의미도 달라졌다. `privacy_cells()`에는 `_read_sample` 처리 경로가 없었고, 창보다 큰 단일 칸을 읽기 참조로 처리할 수 없었다. 세 경로 모두 같은 읽기 보존 방식을 적용했다.

축 분석 묶음별 비용 경계도 없었다. 둘러보기 몫은 유지됐지만 첫 축 묶음의 읽기와 교정 호출이 전체 잔액을 소진할 수 있었다.

## 함께 확인한 입력 손실과 유지한 경계

추가 읽기를 반환했다는 이유로 같은 응답의 정상 축이나 안전한 칸을 무시하던 분기를 고쳤다. 축 분석, 의미 합치기와 가림에서 정상 부분 답을 먼저 보존한다. 의미 합치기의 대기 축 감소와 가림 교정으로 입력이 바뀌어도 읽은 원문 고정 참조는 유지한다. 둘러보기의 성공한 읽기도 다음 행동 입력에서 사라지지 않도록 했다.

표본 미리보기와 문맥의 부분 창은 전체 원문 참조, 범위와 잘림 표시가 있어 유지했다. 필수 상태와 전체 참조가 창보다 클 때는 잘라 버리지 않고 기존 `state_exceeds_window`를 유지한다. 어댑터의 두 번째 앞부분 절단을 다시 넣지 않았다. 가림 실패 칸 분할, 운영자 자격의 정확한 값 치환, GET/HEAD 경계, 폼 제출 금지, 외부 최상위 이동 금지와 사람 확인 경계도 유지했다. 코드가 웹 내용의 중요도, 충분성이나 같은 페이지의 유용성을 판정하는 규칙은 추가하지 않았다.

FIX2의 현재 상태 우선 문맥, 둘러보기 몫, 모델의 멈춤 판단과 결정 전후 체크포인트를 유지했다. `FIX2-REPORT.md`는 수정하지 않았다. 감독자가 추가한 브라우저와 HTTP 대체 경로의 `SITE_ANALYSIS_PROXY` 처리도 그대로 남아 있다(`observer.py:495`, `observer.py:539`).

## 실행한 확인

작업 디렉터리는 `defense/web-proxy-defense/`다. 소스 실행 확인은 아래 `py_compile`과 `--dry-run`만 수행했다.

```powershell
python -B -m py_compile site_analysis/__init__.py site_analysis/catalog.py site_analysis/model.py site_analysis/prompts.py site_analysis/record.py site_analysis/windows.py site_analysis/observer.py site_analysis/analyze.py
python -B -m site_analysis.analyze --origin-url http://target.test/ --out site_analysis/offline-analysis.json --dry-run
python -B -m site_analysis.analyze --origin-url http://target.test/ --out site_analysis/offline-analysis.json --runs 1 --rates ../../.tmp/installer-targets/wordpress/settings.json --max-cost-usd 4 --browse-share 0.5 --context-chars 80000 --max-pages 25 --same-failure-limit 8 --login-env SITE_ANALYSIS_DRY_RUN_UNSET --dry-run
```

초기 dry-run은 새 회귀 검사에서 숫자 0의 문자열 표현 `0`과 `0.0`을 비교해 실패했다. 숫자로 비교하도록 검사 조건을 고친 뒤 기본 dry-run이 종료 코드 0으로 통과했다. 이후 읽기 참조 메타데이터와 재시도 잔액 처리까지 반영한 최종 소스에서 8개 모듈의 컴파일과 4달러, 1회 dry-run을 다시 실행했고 둘 다 종료 코드 0이었다. 단가 파일은 형식과 선택 모델 설정만 확인했으며 최신 공급자 단가는 조회하지 않았다.

dry-run은 로컬 응답 객체와 공급자 실행부를 대체한 로컬 어댑터로 실제 읽기, 축 분석, 가림, 합치기와 호출 전 비용 검사 경로를 확인했다. 실제 Codex CLI, Playwright와 HTTP 클라이언트는 실행하지 않았다.

- 두 읽기 창이 최신 순서로 함께 전달되고, 작은 창에서도 오래된 창의 참조와 범위가 남는다. 서로 다른 `provided-context`를 읽은 뒤 이전 원문 뒤쪽을 다시 읽을 수 있다.
- 같은 창을 성공적으로 다시 읽어도 기록이 중복 증가하지 않는다. 고정 참조 메타데이터를 포함한 창과 base64 재읽기가 지정 길이 안에 들어간다.
- 두 페이지를 읽고 받은 정상 축을 유지한다. 묶음 몫 소진 뒤 마지막 호출은 한 번이며, 그 응답에 `_read_sample`이 있어도 실행하지 않는다. 정상 축 둘은 남고 나머지 축만 오류가 된다.
- 앞 묶음의 미사용액이 다음 몫을 늘린다. 전체 잔액이 적으면 배정액도 줄어든다. 교정 재시도 전 몫을 검사하고 실제 남은 금액을 교정 입력에 반영한다.
- 마지막 호출이 실패해도 재시도하지 않는다. 총 상한에 도달하면 마지막 호출도 실행하지 않는다.
- 가림과 의미 합치기도 여러 읽기 창과 정상 부분 답을 보존한다. 실패한 칸과 안전하지 않은 칸만 분리한다.
- FIX2의 현재 위치와 방문 기록, 최신 표본, 결정 메타데이터와 전후 체크포인트, 둘러보기 몫, 51개 축 형식, 의미 합의와 읽기 안전 경계 검사가 함께 통과했다.

최종 dry-run 출력은 `network_requests=0`, `model_calls=0`, `files_written=0`, `login_values_read=false`였다. 지정한 `offline-analysis.json`과 `.dry-unused` 디렉터리가 생기지 않았음을 파일 존재 검사로 확인했다. `py_compile`은 `site_analysis/__pycache__/` 안에 컴파일 파일을 쓴다.

자료 확인에는 PowerShell 읽기와 `rg`를 사용했다. 시작과 끝의 `git status --short`에서 범위 밖의 기존 변경 목록이 같음을 확인했다. 이 디렉터리는 작업 시작 때부터 git 미추적 상태여서 일반 `git diff`에는 파일별 변경이 나오지 않는다. 수정 내용을 소스로 다시 읽어 검토했다.

## 실행하지 않은 것과 남은 한계

원본과 중계 접속, 실제 모델 호출과 가림, 브라우저 실행, 로그인, Docker 명령, 별도 테스트 실행, 의존성 설치, git commit, push, stash를 하지 않았다. `defense/web-proxy-defense/site_analysis/` 밖은 수정하지 않았으며 별도 테스트 파일도 만들지 않았다.

실제 WordPress에서 반복 읽기가 줄어드는지, 모델이 근거가 충분할 때 답하는지, 각 축의 실제 답과 가림 정확성은 이번 작업에서 확인하지 않았다. 비용은 공급자 사용량을 받은 뒤 정산하므로 진행 중 한 호출이 묶음 몫이나 총 상한을 넘을 수 있다. 다음 호출과 재시도는 막지만 진행 중 호출의 과금을 강제로 끊지 못한다. 마지막 호출도 다음 묶음의 몫을 줄일 수 있다. 총 비용, 시간이나 같은 실패 반복 경계가 먼저 소진되면 마지막 호출을 보내지 않는다.

축 답은 기존 안전 경계에 따라 가림을 통과해야 공개한다. 축 분석 뒤 총 잔액이 없으면 이미 메모리에서 얻은 답이라도 공개 가림을 완료하지 못해 해당 축을 `못 얻음`으로 남길 수 있다. 가림 예산을 임의 비율로 추가 예약하거나 가림을 생략하는 정책은 넣지 않았다. 필수 상태와 참조 목록 자체가 창보다 클 때의 공급자 수용 여부도 실제 호출 없이는 확인하지 못한다.
