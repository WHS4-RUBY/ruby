# 분석기 2026-10-10 개선과 세 웹 실행 보고

## 1. 요약

- WordPress, Gitea, Redmine 원본을 익명 2회, 운영자 준비 계정 세션 2회로 분석하고 같은 권한끼리 합쳤다. 결과 파일은 `.tmp/site-analysis/<이름>.json`이다.
- 세 웹 모두 완료됐다. 모든 회차가 축 53개에 답했고, 이어서 할 일(resume_pending)은 남지 않았다. 결과는 6절에 있다.
- 세 결과 모두 미끼웹 생성 쪽 dry-run에 넣어 연결을 확인했다. 축, 권한별 합친 결과, 사실 표시, 분석 계정 제거 인계, 응답 시간이 넘어가고 값 필드는 0건이다.
- 실행 중 결함 10여 건을 발견해 원인을 확인하고 고쳤다(4절). 대부분 대규모 실행에서만 드러나는 문맥 크기, 파일 교체, 가림 형식, 읽기 반복 문제였다.
- 1회차 결과를 검토자와 검증자가 원자료로 대조해 52건을 찾았다. 프롬프트를 고쳐 모든 회차의 축 분석을 다시 했다. 최종 재검토에서 대부분 일부만 고쳐졌다(5절).
- 운영 문제: 계정 세션 회차에 쓴 계정이 분석 전용 일반 계정이 아니다. Redmine과 Gitea는 관리자 계정이고, WordPress는 공개 글 작성자 계정이다. 분석 결과의 제거 인계가 이 계정을 지우라고 지시하므로, 미끼를 만들기 전에 운영자 결정이 필요하다(7절).

## 3. 바꾼 것

### 3.1 프롬프트 (`prompts.py`)

- 목적: 화면을 다시 만드는 방법이 아니라, 자료와 설정과 신원을 바꾼 뒤에도 관찰된 화면과 공개 범위가 유지되도록 무엇을 누구에게 보여 주는지를 적는다.
- 범위: 사실마다 관찰 권한, 본 화면 종류와 수, 표시 조건, 열지 않은 화면을 적는다. 관찰과 추론을 구분한다.
- 참조와 값: 근거마다 관찰 참조를 회차 번호와 함께 단다. 값은 종류를 밝힌 자리표시로 바꾸고 값의 일부도 남기지 않는다.
- 운영자 세션: 열쇠, 계정 설정, 관리 영역을 열지 않는다. 세션이 풀린 화면은 계정 관점으로 기록하지 않는다.
- 둘러보기: 작업 메모(working_notes)로 찾은 화면 종류와 열지 않은 종류를 이어 간다. 세션에 남는 필터를 메모한다. 같은 폼을 반복 검사하지 않는다.
- 축 분석:
  - 못 봄이나 사례 부족을 쓰기 전에 열었던 해당 화면을 읽는다.
  - 같은 화면을 두 번 잡은 기록은 한 화면으로 센다.
  - 세션 필터로 줄어든 목록을 빈 자리로 적지 않는다.
  - 원본 고유 값이 나오는 자리를 빠짐없이 적는다(절대 주소, 이름과 별칭, 개인 정보에서 만든 식별자, 경로 속 식별자, 설치 기본 계정 이름).
  - 공개 범위 표시를 사실로 적는다.
  - 답할 수 있는 축은 읽기 요청과 함께 먼저 답한다. 묶음 메모(_notes)를 남긴다.
- 가림: 민감한 부분만 자리표시로 바꾼다. 확신이 없으면 비공개로 한다. 바꿀 것이 없으면 safe=true만 돌려주고 값은 생략할 수 있다.
- 합치기:
  - agreement는 두 회차가 확인한 사실이 하나 이상 있다는 요약값이며, 축 전체의 사용 승인이 아니다.
  - 사실마다 both-runs, single-run, contradictory를 붙인다. both-runs는 각 회차의 그 축 답에 그 사실이 있을 때만 붙인다.
  - 같은 권한끼리만 비교한다. 반복된 추론은 관찰로 올리지 않는다.

### 3.2 축 목록 (`axes.json`, 판 1.1)

- 새 축: data_dependent_parts(자료에 따라 나타나는 화면 부분), people_and_names_exposure(화면과 주소에 드러나는 사람).
- 넓힌 축: path_groups, item_sets, permission_levels, legal_operator, source_content, external_connections.

## 5. 결과 검토

### 5.1 1회차 검토 (재분석 전)

검토자와 검증자 각 3명이 원자료와 원본 화면을 대조했다. WordPress 21건, Gitea 19건, Redmine 12건이 나왔다. 검증자가 반박한 것은 없다. 공통 원인은 두 가지다. 관찰해 놓고 분석에서 읽지 않은 것과, 세션에 남은 필터 상태를 원본 상태로 본 것이다.

### 5.2 WordPress 최종 재검토

- 21건 중 일부 고쳐짐 13건, 안 고쳐짐 8건이다. 완전히 고쳐진 것은 없다.
- 남은 대표 사례:
  - canonical: 4개 회차 모두 "못 봄"으로 적었고, 합친 결과도 두 회차 확인으로 굳었다.
  - 본문 속 관리 화면 링크가 빠졌다.
  - 피드의 마지막 수정 시각 관계가 빠졌다.
  - 근거 번호 체계가 섞여 있다.
- 새로 확인된 것:
  - 3회차 31축이 근거에 다른 회차 번호를 붙였다. 회차 번호를 문맥에 넣도록 고쳤고, 다음 실행부터 적용된다.
  - 합치기 표시 오류가 있었다. 합치기 프롬프트를 보강하고 WordPress 합치기를 다시 했다.
  - 공개 기록에 원본 호스트 이름(2회차 헤더)과 페이지 식별자(3회차 결정 기록)가 남았다.
  - 운영자 준비 분석 계정이 공개 글의 작성자 계정과 같다.

### 5.3 Redmine 최종 재검토

- 12건 중 고쳐짐 1건, 일부 고쳐짐 9건, 안 고쳐짐 2건이다. 다른 권한끼리 섞은 흔적은 없다.
- 1회차의 "필터가 남은 빈 피드"는 합친 결과에서 1회차에만 있는 사실(single-run)로 표시됐다. 메움 근거에서는 빠지지만, 1회차 답의 빈 자리 목록에는 단서 없이 남았다.
- 새로 확인된 것:
  - 세션 계정이 설치 기본 관리자다.
  - 공개 기록의 2회차 결정 기록에 원본 프로젝트 식별자가 남았다.
  - 보고서 화면은 0을 "-"로 표시하는데, 합친 결과는 "0건"으로 적었다.

### 5.4 Gitea 최종 재검토

- 19건 중 고쳐짐 3건, 일부 고쳐짐 11건, 안 고쳐짐 5건이다. 다른 권한끼리 섞은 흔적은 없다.
- 고쳐진 것: 사람 노출 자리(이슈 작성자, 프로필, 활동, 아바타), 작성자 역할 표시, 정렬 기준.
- 안 고쳐진 것: 빌드 해시가 붙은 자원, 저장소 코드 검색 폼, 활동 그래프 자료 경로, 위키를 로그인 유도로 오독한 것.
- 새로 확인된 것:
  - 세션 계정이 사이트 관리자 메뉴가 보이는 계정이며, 저장소 소유자이자 유일한 계정이다.
  - 두 익명 회차가 모두 본 빈 자리(변경 요청 0건, 배포본과 태그 0건, 빈 위키)가 합칠 때 single-run이나 contradictory로 낮아졌다. 합치기 모델이 관찰이 아니라 각 회차의 답 문장만 비교하기 때문이다. 메움이 both-runs만 쓰면 이 자리를 비워 두지 못할 수 있다.
  - 2회차가 링크에 없는 주소를 만들어 열어 404를 받았다(규칙 위반).
  - 세션 회차 일부 runtime 축이 기록된 응답을 읽지 않고 못 봄으로 남았다.
  - 세션 화면의 사용자 디렉터리에 메일이 보이는데, 제거 자리로 적히지 않았다.

## 7. 남은 한계

- 축 분석 모델이 열어 둔 화면을 여전히 일부만 읽는다. 프롬프트로 줄였지만 없어지지 않았다.
- 합치기 모델은 각 회차의 답 문장만 비교한다. 두 회차가 모두 관찰했어도 한 회차의 답이 그 사실을 적지 않으면 single-run이 된다. 메움이 both-runs만 쓰면 원본의 빈 자리를 놓칠 수 있다.
- 근거 참조 이름 체계가 두 가지(samples의 screen-N과 buffers의 screen-N)라 서로 다른 화면이 같은 이름을 가질 수 있다. 코드 쪽 문제로 남겼다.
- 상태 파일이 회차와 읽기 창을 모두 담아 160~230MB로 커진다. 저장할 때마다 전체를 다시 쓰므로 재개와 가림이 느리고 메모리를 많이 쓴다.
- 축 분석과 합치기 단계에는 모델 답의 형식 검사(상태 네 값, 일치 값 자료형)가 남아 있다. 이번 실행에서 문제를 일으키지는 않았다.
- 운영자 준비 계정은 분석 전용 일반 계정이어야 한다(계획 01 9절은 관리자 계정을 받지 않는다고 정한다). 이번 실행의 계정은 다음과 같다.
  - Redmine: 설치 기본 관리자 계정이며, 익명에게 보이는 유일한 이슈 작성자다.
  - Gitea: 사이트 관리자 메뉴가 보이는 계정이며, 저장소 소유자이자 유일한 계정이다.
  - WordPress: 공개 글 작성자 계정이다.
  - 분석 결과의 removal_handoff는 이 계정을 미끼에서 반드시 지우라고 지시한다. 그대로 미끼를 만들면 작성자나 관리자가 사라진다.
  - 운영자가 분석 전용 일반 계정을 원본에 만들고 세션 회차를 다시 돌리거나, 이번 결과를 쓸 때 제거 인계를 운영자가 바로잡아야 한다.
- 공개 기록 일부에 원본 호스트 이름과 페이지, 프로젝트 식별자가 가려지지 않고 남았다(결정 기록과 일부 헤더). 기록은 저장소 밖 `.tmp`에 있지만, 공개 전에 다시 가려야 한다.
- 계정 세션 회차의 사실 칸은 가림 모델이 대부분 비공개로 판단했다.
- 재개할 때 끝난 단계를 확인하며 상태 파일을 매번 다시 쓰므로, 큰 웹은 다시 시작한 뒤 실제 작업까지 약 15분이 걸린다.

## 8. 다음 단계

1. 운영자 결정: 분석 전용 일반 계정을 준비할지, 이번 결과의 제거 인계를 고칠지 정한다.
2. 근거 참조 이름 체계를 하나로 합친다(코드).
3. 상태 파일에서 관찰 원문과 진행 상태를 나눠, 저장과 재개를 가볍게 한다(코드).
4. 미끼웹 생성을 새 분석 결과로 다시 돌린다. Redmine은 새 사본에서 돌린다.
