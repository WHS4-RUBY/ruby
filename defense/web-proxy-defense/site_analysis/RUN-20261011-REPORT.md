## 요약

이전 실행의 최종 재검토에서 안 고쳐짐은 WordPress 8, Gitea 5, Redmine 2건이었다.

등급 정정: Gitea 1회차가 실행하지 않은 별표 동작을 "실행해 로그인 요구를 확인했다"고 서술한 항목은 검증 AI가 미끼 영향이 작다며 중으로 판정했다. 그러나 등급 기준은 "안 본 것을 본 것처럼 서술"을 상으로 정한다. 기준 문구에 맞춰 상으로 정정한다.

영향 서술의 한계: 재검토의 "미끼 영향" 서술 일부는 분석 오류가 곧 미끼 차이로 이어진다고 가정했다. 미끼는 원본 프로그램을 복사하므로, 분석 오류가 미끼를 바꾸는지는 메움과 검증이 그 답에 의존하는지에 달려 있다. 이번 재검토는 관찰 정확성을 판정했고, 후속 영향도는 따로 확인하지 않았다.

정정 전 중 13건의 유형:
- 관찰한 사실을 덜 적거나 "못 봄"으로 적음: 9건(빈 설정값, 같은 본문 반복, 받은 CSV 내용, 쓰기 링크 일부 등)
- 계산 오류: 2건(링크 깊이, 시각 차이)
- 화면에 버튼이 없는 숨은 폼을 쓰기 기능으로 적음: 1건
- 실행하지 않은 동작을 실행한 것처럼 서술: 1건(Gitea 1회차, 별표 동작)

하 23건 중 다수는 같은 내용에 회차마다 다른 상태값(관찰됨, 사례 부족, 못 봄, 없음)을 붙인 경우다.

- 미확정 표시(final)를 미끼웹 생성 입력으로 전달

- 응답 색인 위치를 제공 순서 기준으로 고침

## 2차 교차검증 반영

외부 교차검증이 1차 지적의 해결 여부를 합성 시험으로 다시 확인했다. final 전달, 진단 원문 제외, 소비자의 추가 필드 보존, 응답 색인은 해결로 확인됐다. 남은 것과 새로 생긴 것을 고쳤다.

| 지적 | 수정 |
| --- | --- |
| 입력 해시가 없는 이전 가림 결정을 그대로 승인 | 해시가 없는 결정은 현재 입력과 맞는지 알 수 없으므로 다시 검토한다. 공개 불가 표시에도 입력 해시를 기록한다 |
| 본문 재수집이 전체 본문을 받은 뒤 잘라 저장하고 잘림 표시가 모순 | 전송 크기가 본문 한도 이하일 때만 재수집한다. 넘으면 못 얻음으로 기록한다. 받은 본문은 한도로 잘라 두고 잘림 표시가 실제 보관량과 맞게 한다 |
| 끝난 묶음의 읽기 창을 지우면서 근거 참조가 끊김 | 창 본문만 지우고 창의 출처(원래 관찰 참조와 범위)는 남긴다 |
| 읽기 묶음 1/3 상한이 실제 상한이 아님 | 창마다 남은 공간으로 읽기 길이를 줄인다 |
| Windows 오류 범위 전체를 시작 실패로 보고 0달러 확정 | DLL 초기화 실패와 DLL 없음(0xC0000142, 0xC0000135)만 시작 실패로 본다. 다른 코드는 추정 비용으로 남긴다 |
| 없는 참조 찾기가 0건 검색으로 표시되고 반복 한도에 안 잡힘 | 없는 참조를 따로 표시하고 반복 한도에 넣는다 |
| 한도보다 큰 원문이 기존 사본을 먼저 지운 뒤 오류 | 비우기 전에 거부한다 |

## 감사 반영(2026-10-11 새벽)

2차 교차검증 반영 뒤 두 감사의 지적을 코드 여섯 파일(analyze.py, observer.py, prompts.py, record.py, session_prepare.py, windows.py)에 반영했다. 감사 1(숨은 제한)은 코드가 고정 목록, 개수 상한, 내용 분기, 열거값, 검증으로 자료를 조용히 버리거나 내용을 판단하는 곳을 찾았다. 감사 2(범용성 가정)는 구조가 다른 웹에서 깨지는 가정을 찾았다. 표에 없는 지적은 이 PR에서 고치지 않았다. 위의 실행과 재검토는 이 절의 변경 전 코드로 진행됐다. 28~33번은 그 뒤 작은 실행(아래 "작은 실행 확인")과 수정 검증에서 드러난 결함, 감사 기록에 남아 있던 지적을 고친 것이다.

감사 1의 항목 ID는 검증 단계의 표기다. 렌즈마다 F 번호가 겹쳐서 고정 키 렌즈는 K-F, 상한 렌즈는 L-F, 내용 값 분기 렌즈는 번호 뒤 a, 검증과 거부 렌즈는 번호 뒤 b로 구분한다. 같은 문제를 여러 항목이 지적한 경우 ID를 함께 적는다.

## 한계

- gitea-analysis-3의 1~3회차와 4회차 앞부분, redmine-analysis-3의 1~4회차는 A9 수정 전에 둘러봤다. 정적 자원 본문이 빈 채로 기록돼 있다. HTML 화면과 소스는 정상이다.
- 같은 회차들의 축 분석은 응답 색인 수정 전이다. 색인 번호로 응답을 찾은 경우 다른 응답을 봤을 수 있다. 요청별 직접 참조는 정상이었다.
- 합친 결과(both-runs 표시)는 wordpress-analysis-7에서만 나왔고 이번 재검토 범위에 들어가지 않았다.
- 가림 결정 중 입력 해시가 없는 것(수정 전에 내린 결정)은 이어서 실행할 때 다시 검토된다. 그 전까지의 가림 결과는 확정 입력으로 쓰지 않는다.
- 실행 도중 코드를 여러 번 바꿨다. 상태 파일에는 단계별로 어느 코드판이 처리했는지가 기록돼 있지 않다.
- 수정별 회귀 시험은 없다. 확인은 --dry-run 자체 점검, 실제 브라우저 확인(A9), 실제 실행에서의 재발 관찰이다.
- 다음 비효율은 안정성 위험 때문에 고치지 않았다: 호출마다 상태 파일 전체 저장, 재시작 때 전체 재저장, 웹 안의 직렬 처리, 가림 호출의 전체 문맥 전송.
